# Mirrorball Madness

Fantasy sports app for Dancing with the Stars. Next.js 15 (App Router), TypeScript, Tailwind CSS v4, Shadcn UI (base-nova style, built on Base UI), Supabase (Auth + Realtime + Postgres).

Schema: [supabase/schema.sql](supabase/schema.sql) is the source of truth — it's applied directly to the Supabase project via `psql` (no migration files/CLI linking yet). After any schema change, regenerate `src/lib/supabase/types.ts` so query results stay correctly typed:
```
npx supabase gen types typescript --project-id wssbwgtsejamlbvfofvu --schema public > src/lib/supabase/types.ts
```
(Needs a `SUPABASE_ACCESS_TOKEN` env var — a personal access token from supabase.com/dashboard/account/tokens — since this container has no Docker for the local-introspection path.)

Full concept and phased build plan live in conversation history until they're worth codifying here.

Session continuity: [MEMORY_HANDOFF.md](MEMORY_HANDOFF.md) tracks the most recent working session's state (what changed, why, what's still unverified, what's next) — read it at the start of a new session before assuming this file alone has full context, and keep it updated as work wraps up.

## Rules

- **Write clean code.** No dead code, no speculative abstractions, no comments explaining *what* code does — only *why*, when the reason isn't obvious from the code itself.
- **Respect the dev container setup.** This project runs inside `.devcontainer/devcontainer.json`. Don't work around it (e.g. installing global tools outside the container, hardcoding host-specific paths). If the container config itself needs to change (new port, new dependency), edit `devcontainer.json` rather than patching around the gap.
- **Never put API keys, secrets, or credentials in code files.** All secrets go in `.env.local` (already gitignored) and are read via `process.env`. If a new secret is introduced, add its key (not its value) to `.env.example` so the shape is documented without leaking anything.
- **Test changes before finishing.** Before considering a task done: run the dev server or build (`npm run build`) and confirm it succeeds, run lint, run `npm test` (Vitest, against pure-logic helpers under `src/lib/`) if the change touches pure logic, and exercise the actual feature path (not just "it compiles") when the change is user-facing.
- **Update project documentation as features are added.** Keep this file and any relevant docs (schema comments, README) in sync with what the app actually does — don't let them drift into describing a past version of the app.

## Architecture & Conventions

- **Every user-facing write goes through a `SECURITY DEFINER` Postgres function**, never a direct table write from the client. Because these run with `set search_path = ''`, every reference inside them must be schema-qualified (`public.leagues`, `auth.uid()`, etc.) — an unqualified table name will fail to resolve. Authorization lives inside the function body (`auth.uid()` checks), not in RLS alone — RLS on these tables is read-scoping, not write-scoping.
- **Column-level grants, not blanket ones, for self-editable rows.** `profiles` only grants `UPDATE (display_name, avatar_url)` to `authenticated`, not a blanket `UPDATE`, because RLS's "owner" policy only checks row ownership — a blanket grant would let a user set *any* column on their own row, including `is_super_admin`. This was a real, self-exploitable bug in production before it was caught. Follow the same pattern for any future self-editable column that shouldn't be user-writable.
- **Server actions split logic from authorization.** Non-trivial write logic lives in a plain exported function in `src/lib/*.ts` (DB-free where possible, or taking an already-authorized client); the `"use server"` action wrapping it is thin — just the "who's allowed" check plus a call into that function. This is what makes the logic callable from a test script directly, without a live Next.js request context (server actions can't be invoked that way — they need cookies/request scope).
- **Data model facts that don't change with any UI redesign:**
  - `roster_slots` is a *timeline*, not a snapshot: one row per occupancy period, current occupant is the row with `end_week is null`. Never assume one row per manager-slot.
  - `people` unifies celebrities/pros/judges under one table (`role` column) so the same real person across seasons/dances is one row, not re-typed text. Scoring judges use `people.archived_at` as a soft-hide (null = standing panel / empty score box). Do not hard-delete a judge who has `judge_scores` history — archive them so past weeks still display and later weeks drop the empty box. Rename updates `people.name` only; `judge_scores` / `draft_judge_scores` join on `judge_id`, so history stays attached (and will show the corrected name). Celebrities/pros leave `archived_at` null; they are season-scoped via `couples`.
  - Every `league_id → leagues(id)` foreign key cascades on delete; **no** `manager_id`/`user_id`/`commissioner_id → profiles(id)` foreign key does. Deleting a league cleans up completely; deleting a profile/auth user does not (and will fail outright) if that person has any league history anywhere.
  - `leagues` are not season-scoped — a league persists across seasons; only `couples`/`episodes` (and anything keyed to them) carry a `season_id`, resolved via `active_season_id()`. Any new couples/episodes-related query should ask "does this need `season_id = active_season_id()`?"
  - **Episode vs Week:** an Episode is one TV airing (`episodes.episode_number` unique per season — `S35 E01`). A Week is a fantasy competition round (`competition_weeks.week_number` unique per season). Premiere Night One + Night Two are two episode rows under Week 1 (`episodes.week_id`). Exhibition / interview nights leave `week_id` null and never appear on Results/Picks. Do **not** reintroduce `week_part` and do **not** fold two airings into one episode row (that was the rejected Option A / PR #28). **Admin / site-ops** copy uses `formatEpisodeLabel` (`S35 E02`) on Schedule episode rows. **Fan tabs** (Home / Results / Picks / Standings) use the casual helpers in `src/lib/format-week.ts`: `Week N` / `Week N — {theme}`. Multi-episode weeks may add a subtle `Night One + Night Two` (`formatNightsLabel`). Don't hand-roll either form. Predictions, `weekly_manager_scores`, spoiler progress, and elim outcomes key off `week_id`; dance scores stay on `episode_id`. Live schema change: owner-run `supabase/apply-competition-weeks.sql`.
  - Results (`/this-week`) and Picks share the slim ← `Week N — {theme}` → `EpisodeCarousel` (`?week=` is `competition_weeks.id`). Results flipping is `/this-week?week=` plus `resolveSpoilerCutoff`: visible completed weeks show results; upcoming/locked weeks are a theme peek; unwatched completed weeks are not selectable. Picks flipping is `?tab=yourpicks&week=` on one Curtain Call card — live week is the pick form, completed weeks are the recap (unwatched stay on the lock card). Home has no week carousel, but does carry a compact `EpisodeBanner` (`src/components/episode-banner.tsx`, state from `computeEpisodeBannerState` in `src/lib/episode-banner.ts`): "Week N" numeral, picks-open / on-air status, and season-progress dots. It shows the *show's* `earliestAirsAt` (not a lock time — those are per-league), derives "on air" from `airs_at` (nothing writes `episodes.status = 'locked'`), drops picks wording when no league has Curtain Call on, hides when there's no live week, and collapses into a slim sticky bar on scroll. A week is completed only when every assigned episode is completed.
  - Admin Schedule still **adds episodes**, grouped under week headers (title is **Schedule**, not “Scheduled Episodes”). No “Competition week” checkbox — blank week number = exhibition. Enter/View Results chrome is by Week, not leading with S35 E0x; admin can still show S35 E0x on episode rows inside Schedule and nested under a multi-night week. Unpublished episodes offer the currently-active cast only (so an already-eliminated couple can't be re-ticked onto next week). Published weeks keep whoever was still in as of that week (`elimination_week >= week_number`) so View Results / corrections don't lose the couple who went home that night. Helpers live in `src/lib/episode-cast.ts`.
  - Auto-draft v1 is random-only among eligible remaining couples (`make_auto_draft_pick`). Timeout uses `leagues.current_turn_started_at` + `pick_time_limit_seconds`; sit-out is `league_members.draft_autopilot`. Any league member may invoke the RPC so a started draft still moves if the picker never joined — it never *starts* a draft. `draft_picks.is_auto` is the log flag (`auto · random`). Commissioner `undo_last_auto_pick` deletes the latest auto-pick only while the draft is still in progress.
  - Recast / fan roster occupancy reuses `spoilerSafeCoupleStatus` / `resolveSpoilerCutoff` — do not key Recast copy or waiver open-slot names off raw `eliminated`/`withdrawn`. `classifyRosterOccupancy` / `partitionRecastSlots` (`src/lib/recast-framing.ts`) hide unrevealed elims (vague catch-up card, no `formerCoupleName`). Once revealed, Recast works as before and `clampRosterCoupleForWeek` zeros later-week roster points so a gone couple cannot keep scoring as active. Pick 'Em and the waiver wire use `isSpoilerSafeActive` so the same couple stays in the pool until the elim week is allowed.
  - **Grand Finale ranks the whole season cast** (eliminated couples included — `submit_grand_finale_prediction` requires every couple once) and stays open until the hard deadline. Couples whose elimination is already *revealed* to the viewer (`spoilerSafeCoupleStatus`) are pinned first in the ranking by `pinEliminatedFirst` (`src/lib/grand-finale-pins.ts`) and can't be moved, so only the still-competing couples are ranked; unrevealed eliminations stay unpinned to avoid spoilers. Pinning is UI-only, the RPC doesn't enforce it.
  - Account deletion is request-and-review. `request_account_deletion` stamps `profiles.deletion_requested_at`; the super-admin queue is `/admin/accounts` (strict `is_super_admin` — never `RESULTS_ENTRY_OPEN_TO_ALL`). “Clear request” only nulls that column. Do not auto-delete `auth.users` or cascade-wipe leagues — historical scores stay woven into other members' standings. Dashboard one-off: `supabase/queries/pending-account-deletions.sql`.
  - **Scoring calibration**: `scoring_settings`'s point values (survival, elimination/top-scorer prediction, placement bonuses, bonus-picks-per-correct) are ordinary commissioner-editable columns, but their *defaults* are calibrated, not hand-picked — see `scripts/monte-carlo-calibration/` (plain Node, no `tsx` in this repo) and re-run it against real season data before trusting its numbers for a new season. `judges_score_multiplier` is the one roster-size-keyed constant (`dance_card_calibration` table, read once by `start_draft()` when `roster_size` first fixes — guarded by `judges_score_multiplier_customized` so it never clobbers a commissioner's own override). A couple finishing the finale's top 5 pays a *split* placement bonus: `first_place_points`..`fifth_place_points` is the Dance-Card-half (weighted by `judges_score_category_weight`), `bonus_picks_first_place_points`..`bonus_picks_fifth_place_points` is the Grand-Finale-half (weighted by `bonus_picks_category_weight`) — both computed in `computeWeeklyScores` from a caller-supplied numeric `finalPlacement` (1-5), not from `couples.status`. Curtain Call's elimination/top-scorer guesses both scale by `couplesRemaining / totalCouples` (`curtainCallPayout` in `src/lib/scoring.ts`) — correctly calling an elimination from 12 couples pays more than from 4; the picking UI (`pick-em-box.tsx`) renders the identical preview via the same shared helper so it can't drift from what's actually scored.

## Environment Gotchas

- **No live database credentials in this container.** Schema/RPC changes are written to a `.sql` file, handed to the user to run via the Supabase Dashboard SQL Editor, then verified afterward with the service-role key. Never wrap SQL in a bash heredoc when handing it over — paste it as a plain `.sql` file or fenced block only.
- **Integration-test against the live project with real throwaway accounts**, not service-role bypass — most RPCs check `auth.uid()`, which a service-role call never populates. Pattern: `admin.auth.admin.createUser()` + anon client `signInWithPassword()`, always cleaned up (including the throwaway `auth.users` rows) in a `finally` block.
- **Ad-hoc verification scripts must run from the project root**, not a scratchpad directory — otherwise ESM `import` of `@supabase/supabase-js` fails to resolve `node_modules`. Also needs `NODE_OPTIONS="--experimental-websocket"` on Node 20, or `@supabase/supabase-js`'s realtime client throws "native WebSocket not found" even for scripts that never touch realtime.
- **`league_members.role` only accepts `'commissioner'` / `'manager'`** — not `'member'`. Inserting `'member'` fails the check constraint silently if the calling code doesn't check the error.
- **A stale `tsconfig.tsbuildinfo` can make `next build`'s type-check fail with an error that doesn't match current source.** If that happens and `npx tsc --noEmit` passes clean, `rm -rf .next` and retry before assuming the code is broken.
- **This repo often has more than one thing in flight** (e.g. the iOS Capacitor wrapper's `project.pbxproj`, or a parallel session's WIP). When committing, stage files by name for the specific change being made — never `git add -A` — so unrelated in-progress work doesn't get swept in or overwritten.

## UI Component Patterns

- **Add new base-nova primitives via the shadcn CLI**, not by hand: `npx shadcn@latest add <name>` (e.g. `tabs`, `sheet`, `dialog`) pulls it already adapted to this project's import paths and styling — don't hand-roll a Base UI wrapper from scratch.
- **Base UI's `Select` needs an explicit `items` prop** (`Record<string, ReactNode>`) or the closed trigger renders the raw value instead of a resolved label. Easy to forget when adding a new `Select`.
- **`Button` composed with `render={<Link .../>}` needs `nativeButton={false}`.** `Button` defaults to `nativeButton={true}`, which assumes it renders a real `<button>`; composing it onto a `Link` renders an `<a>` instead and Base UI logs a console error about it in dev. Pass `nativeButton={false}` on any `Button`/`render`-onto-an-anchor composition (this doesn't apply to `SheetTrigger`/`DialogTrigger` wrapping a `Button` — those still render a real `<button>`).
- **A Base UI `Dialog`/`Sheet`/`Tabs` root supports multiple `Trigger`s** pointing at the same root — no need to lift state manually just to open the same sheet/dialog from two different places on the page.
- **The `cn` helper (from the `cn` package, not raw `clsx`) is tailwind-merge-compatible** — a later conflicting class always wins over an earlier one. Safe to override a generated component's default classes by just passing `className`.
- **Date/time hydration safety**: absolute date/time formatting (anything using the viewer's local timezone) must be computed client-side after mount (`useEffect`, empty deps), never during initial render — the server has no meaningful browser timezone, and computing it during render mismatches the SSR output. *Relative* durations (a countdown, "in 3 hours") have no such ambiguity and are safe to compute directly in a Server Component.
- **Picks section labels vs card titles.** When ≥2 scoring modules are on, section labels are the product titles only (🔮 Curtain Call / 🪩 Dance Card / 🏆 Grand Finale). Dance Card / Grand Finale card titles stay the task phrase (“Your roster”, “Your season ranking”). Curtain Call’s card title is **Curtain Call** (not “This week's picks”, which lies when the carousel rewinds, and not “Picks”, which is the tab). Week identity lives on the slim carousel (`Week N` / `Week N — {theme}`). Draft status cards keep their state titles. Standings and settings still use the product names.
- **Curtain Call picks are dropdowns**, not chip grids: one “Who goes home?” `Select`, two labeled elim dropdowns on a double-elim week, one top scorer. Reuse `@/components/ui/select` (needs the `items` prop).
- **Curtain Call on Picks** is one card (`CurtainCallCard`): title **Curtain Call**, shared `EpisodeCarousel`, body is either `PickEmBox` (live/upcoming week) or the past recap (completed week). Not a second Past picks card. `?tab=yourpicks&week=` plus `resolveSpoilerCutoff` — unwatched completed weeks are selectable but locked. Points come from `weekly_manager_scores.prediction_points`. Hidden when Curtain Call is off.
- **Cross-league picks (Curtain Call + Grand Finale)** are a one-time copy, never a link. Two entry points on the pick forms: **Also save to…** (a collapsed "Also save to N leagues ▾" toggle above Save that opens one tickable row per league, each with its own note; one Save loops `submit_prediction` / `submit_grand_finale_prediction` per league via `submitPredictionToLeagues` / `submitGrandFinalePredictionToLeagues`) and **Use my picks from…** (pre-fills an empty form, never saves). No new SQL — the RPCs stay the authority on membership, module-off and lock; `planDestination` (`src/lib/copy-picks.ts`) only decides what to *offer* (`ok` / `will_replace` / `module_off` / `locked`). Only `ok` leagues start ticked. Pins and the eligible-couple pool are per *viewer*, not per league, so a pre-filled Grand Finale order goes through `adaptGrandFinaleOrder` (→ `pinEliminatedFirst`) and a Curtain Call pick through `adaptCurtainCallPick`. Dance Card is deliberately not copyable (drafts are per-league). Data comes from `loadOtherLeaguePicks` (`src/lib/other-league-picks.ts`).
- **Add to Home Screen how-to** is a top-level Settings row (`/settings/add-to-home-screen`), not nested under Notifications and not on Home. Capacitor / standalone PWA hide the Safari/Chrome steps and show a short "you're already in the app" note. No first-visit modal, no push subscribe button — delivery infra is still backlog. iOS vs Android steps live in `src/lib/add-to-home-screen.ts`.
- **Fan / admin tab bars** stay `fixed` to the viewport bottom on every width (not `sm:static`) and span the `max-w-2xl` content column (not `sm:w-fit`). Shared chrome is `BottomNav` / `FanBottomNav` in `src/components/bottom-nav.tsx`. A second sticky admin bar (Save/Publish) stacks above via `BOTTOM_NAV_STACK_ABOVE`.
