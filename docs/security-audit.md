# Security and access control audit — 2026-10-17

A read-only review of who can read and write what: Postgres grants, RLS and `SECURITY DEFINER` RPCs, server actions, service-role reads, redirects, and the live Supabase Auth config. No app code, schema or config was changed. Every finding below was re-checked by at least one independent verifier, and their corrections are folded into the text.

**How it was checked**
- Read all of `supabase/schema.sql` at HEAD and compared it with the `apply-*.sql` files. Read all 14 server action files and the `src/lib` functions they call, the pages that use the service-role client, the middleware, the `/auth/callback` route and every `?from=` / `?next=` consumer.
- Ran attack scripts against a PGlite copy of the schema with RLS turned on for every table and `auth.uid()` set per call (scratch harness outside the repo: `attack1.mjs`, `attack2.mjs`, then `gap1.mjs` and `gap2.mjs` for the Season Clock null-deadline bypass, late Grand Finale submits between air and publish, unbounded names, and score/bonus range constraints).
- Ran read-only live queries through the Supabase Management API: function ACLs and `EXECUTE` privileges, table privileges and `relacl`, `pg_policies`, the realtime publication, aggregate counts (pending co-manager codes, `locking_exempt`, West-lock leagues, Grand Finale on, open late unlocks), and `GET /config/auth` (non-secret keys only).
- Live drift check: compared every live public function body (`pg_proc.prosrc`) with its last definition in HEAD `schema.sql`, compared live policies with the schema's, and checked that no leftover `apply-*.sql` functions (`undo_last_auto_pick`, `_sp_*`) are still callable.
- Live accounts, first pass: one throwaway auth user (`audit-security-1@example.test`) was created for read attempts only, then deleted. Afterwards the service role found 0 leftover auth users and 0 leftover profiles. No other live writes.
- Live accounts, gap pass: created 3 throwaway auth users (`audit-secgaps-a/b/c@example.test`). One created a throwaway league, "audit-secgaps throwaway", which another joined and where one minted a co-manager code. This was used to test Realtime delivery of `league_members` changes. Deleted in a `finally` block: the league (its members cascaded), then all 3 auth users. Verified afterwards with the service-role client: `league_members` = 0, `profiles` = 0, leagues named `audit-secgaps*` = 0, and the auth users are gone (0 found). No other live writes; everything else was read-only Management API `SELECT`s and `GET /config/auth`.
- Verifiers additionally made 4 `GET /auth/v1/authorize` probes (302 to Google, transient flow state only), HTTP `HEAD` requests to allow-listed hosts, and one `admin.generateLink` with a throwaway user (cleaned up and verified). No emails were sent.

**Limits**
- Google OAuth identity linking was not exercised. Whether Supabase auto-links a Google sign-in onto an attacker's earlier auto-confirmed password account for the same email (an account pre-hijack) is unverified, so it is not a finding. Only the provable squatting and mass-account effects are (SEC-18).
- The late-entry payout in SEC-7 was proven up to the snapshot (`ineligible_couple_ids` empty). The final points come from reading `eligibleGrandFinalePredictions` and `weekly-score-rows.ts`, not from running a publish.
- `next dev` was not run, so the client-side bounds on score inputs were confirmed only by reading source.
- `auth.identities` counts by provider were not checked (the `auth` schema is outside the read-only scope).
- The gap pass did not re-test items the first pass already covered.
- `reset_draft` deletes every `weekly_manager_scores` row for the league, Curtain Call and Grand Finale included, not just Dance Card. It is commissioner-authorized and more an integrity question than access control, so it is noted here and not reported.

Severity:
- **High:** a real user or attacker can break scoring, see spoilers/peer picks/unreleased scores early, write to data they shouldn't, lose data, or take the site down on a live night.
- **Medium:** wrong behavior or real risk on a common path, or a likely live-night failure with a workaround.
- **Low:** hardening, polish, maintainability with a concrete payoff.

## Findings

**SEC-1 · Live auth redirect allow-list accepts any `*.vercel.app` callback** — High
- **Where:** the live Supabase Auth URL configuration (`uri_allow_list`), not a repo file. Nearest code anchor: [actions.ts:58](../src/app/auth/actions.ts#L58), where the callback URL is built.
- **What's wrong:**
  - The allow-list contains `https://*.vercel.app/auth/callback`. That matches any project anyone can deploy on Vercel, not just this app's.
  - Two other allow-listed hosts no longer serve a deployment: `dwts-fantasy-app-six` returns `DEPLOYMENT_NOT_FOUND` and `dwts-fantasy-app-kylie8` returns 410 `GONE`.
  - An attacker doesn't go through `actions.ts` at all. They build the `/auth/v1/authorize` URL (Google), or a magic-link / `/auth/v1/recover` request, with their own `redirect_to`, and Supabase accepts it because it matches the wildcard. All of these share the same allow-list check.
- **Why it matters:** the redirect target receives the session tokens. A host outside the owner's control on that list puts every user's session at risk. The recovery route matters most: with no custom SMTP, recovery email only reaches project team members, which is exactly the single super admin who publishes results.
- **Fix:** in the Supabase dashboard:
  - Remove `https://*.vercel.app/auth/callback`. The team-scoped preview pattern `https://mirrorball-*-madness-kylie8.vercel.app/**` is already listed, so previews should keep working. Check first whether `dwts-fantasy-mirrorball-madness` previews need their own scoped entry.
  - Remove the dead hosts (`dwts-fantasy-app-six`, `dwts-fantasy-app-kylie8` and its `/**` entry). `-kylie8` carries the account-scope suffix and is unlikely to be claimed by someone else; `-six` is a plain project name that may be re-registrable (unverified). Remove both anyway.
  - Confirm `dwts-fantasy-mirrorball-madness.vercel.app` (live, 200) is the owner's.
  - Keep the `com.kylieau.*` custom-scheme entries for the iOS wrapper. The legacy `com.kylieau.dwtsfantasy://` entry is probably stale (unverified).
  - Deriving `redirectTo` from a configured site URL instead of the `Origin` header is optional hardening only. Next server actions already check `Origin` against `Host`, and the attack never touches that code.
- **Evidence:** read-only Management API `GET /config/auth` showed the allow-list; `HEAD` requests confirmed each host's status. Verifiers reproduced the redirect acceptance with `GET /auth/v1/authorize` probes and an `admin.generateLink` call on a throwaway user (cleaned up). **3/3 upheld.** All three verifiers corrected the original framing: the defect is the live config, not the `Origin`-derived `redirectTo` in `actions.ts`.

**SEC-2 · Fellow league members can read another team's pending co-manager invite code** — High
- **Where:** [schema.sql:1295](../supabase/schema.sql#L1295) (table-wide `grant select on public.league_members to authenticated`); also [schema.sql:148](../supabase/schema.sql#L148) (the column), [schema.sql:1371](../supabase/schema.sql#L1371-L1373) (fellow-member SELECT policy), [schema.sql:2397](../supabase/schema.sql#L2397) (realtime publication), [schema.sql:1349](../supabase/schema.sql#L1349-L1362) (`is_league_commissioner` accepts `co_manager_id`), [schema.sql:1260](../supabase/schema.sql#L1260) (`delete_league`), [schema.sql:2343](../supabase/schema.sql#L2343) (`reset_draft`).
- **What's wrong:**
  - RLS lets any member read every column of every `league_members` row in their league, including `co_manager_invite_code`. A direct PostgREST or supabase-js query with the anon key and the member's own JWT returns other teams' codes.
  - `league_members` is in the realtime publication, and `draft-room.tsx` subscribes to its changes, so the codes also arrive in change payloads.
  - The League Settings page is not the leak. It is a Server Component that selects the column for every row ([page.tsx:44](../src/app/leagues/%5Bid%5D/settings/page.tsx#L44)) but keeps only the viewer's own before rendering ([page.tsx:120](../src/app/leagues/%5Bid%5D/settings/page.tsx#L120)).
  - To redeem, the reader needs a second account outside the league, because `join_as_co_manager` refuses existing members ([schema.sql:1047](../supabase/schema.sql#L1047-L1053)). Anyone can make one by signing up.
- **Why it matters:** whoever redeems the code becomes that team's co-manager with full parity. If it's the commissioner's team, `is_league_commissioner` passes for them too: rename, `delete_league`, `reset_draft`, removing members. One pending code exists on live today (of 26 total).
- **Fix:** there's no column-level revoke from a table grant, so a column-only revoke won't work. Revoke table-level `SELECT` on `league_members` from `authenticated`, then `GRANT SELECT` on every other column (the same column-grant convention `profiles` uses). Serve the owner's own code through a `SECURITY DEFINER` getter, since the settings page reads it from this table today, and check for any `select('*')` reads of `league_members` that would break. Realtime payloads only respect column privileges once the table grant is column-scoped, so this also closes the realtime path. Alternatively, move codes to a table whose RLS limits reads to the owning primary. Consider expiring codes, or having the primary confirm a redemption.
- **Evidence:** PGlite `attack1` T1: member B read A's code by plain `SELECT`; an outsider account redeemed it, submitted a pick that landed on A's team, passed `is_league_commissioner`, and renamed the league. Live read-only queries (`role_table_grants`, `column_privileges`, `pg_policies`, `pg_publication_tables`) matched HEAD; pending codes = 1. Gap pass, live with throwaway accounts: a fellow member received another team's `co_manager_invite_code` over `postgres_changes`, and a non-member received 0 events. **3/3 upheld.** Verifiers corrected the original claim that the page hides codes client-side, and added the second-account precondition. Not covered by ux-audit A3, which is about the league invite page.

**SEC-3 · Scores and Schedule pages send unpublished draft scores and outcomes to any signed-in user** — High
- **Where:** [results-page-data.ts:181](../src/lib/results-page-data.ts#L180-L183) (the service-role `loadDraftForEpisode(admin, …)` call both pages share); [results/page.tsx:40](../src/app/admin/results/page.tsx#L40) and [:73](../src/app/admin/results/page.tsx#L73); [schedule/page.tsx:24](../src/app/admin/schedule/page.tsx#L24) and [:35](../src/app/admin/schedule/page.tsx#L35); [results-draft.ts:196](../src/lib/results-draft.ts#L196-L237) (what a draft contains).
- **What's wrong:** `/admin/results` and `/admin/schedule` are open to every signed-in user (View tier). Both load `draftsByEpisode` with the service-role client for every episode: per-judge draft scores, drafted outcomes including eliminations, and In Jeopardy picks. Both pass it as props into `"use client"` components (`results-screen.tsx`, `schedule-manager.tsx`), so it is serialized into the RSC payload whether or not it renders. Correction drafts for published weeks go out the same way, though they match what's live.
- **Why it matters:** on a live night, any account can read unreleased draft scores and drafted eliminations before publish. That bypasses the service-role-only `draft_*` tables, `draft_couple_releases` and `visible_draft_dance_scores`, and leaks spoilers.
- **Fix:** only send full drafts to propose-tier viewers. Scores needs only `hasDraft` and the entry count (`all-results-view.tsx:216`, `:259`, `:373`); Schedule needs only `hasDraft` and the drafted couple ids (`schedule-manager.tsx:439`, `:454`). Have `loadResultsPageData` return a per-episode summary like `{hasDraft, entryCount, draftedCoupleIds}`, and keep the full `DraftState` for `/admin/results/enter`, which already redirects non-propose viewers before loading anything.
- **Evidence:** code read of the lines above. Live: `authenticated` has no `SELECT` on any `draft_*` table, so these pages are the only path to the data; 0 unpublished drafts exist right now, and the next unpublished episode airs 2026-10-21 00:00 UTC. **3/3 upheld.** One verifier would rate it Medium: draft rows only exist once the East broadcast is airing and picks lock by the end of each league's broadcast, so the leak gives no edge over live TV for picks. It remains a spoiler leak and a bypass of the release gating for any account. `releasedCoupleIdsByEpisode` is also read via the admin client but that table is already granted to `authenticated`, so it is not a leak.

**SEC-4 · Commissioner can reveal peers' pre-lock picks and reopen picks by editing the lock settings** — High
- **Where:** [schema.sql:1433](../supabase/schema.sql#L1433-L1434) (unguarded writes of `prediction_lock_hours_before_air` and `prediction_lock_coast` inside `update_league_settings`, which starts at [:1404](../supabase/schema.sql#L1404)); [schema.sql:2667](../supabase/schema.sql#L2667) (`prediction_lock_at`); the UI controls in [league-modules-form.tsx:802](../src/components/league-modules-form.tsx#L802-L848), which are never disabled.
- **What's wrong:** both lock settings can change at any time, through the normal League Settings UI.
  - Raising the lock hours moves the lock into the past, so RLS shows everyone's predictions to the whole league (not just the commissioner). Lowering them again reopens submissions. Raising them mid-week also instantly locks managers who haven't submitted.
  - Flipping the coast from east to west after the East broadcast reopens `submit_prediction` for the whole league until 8pm PT, after the elimination is public. This is the most serious path. Negative hours can't do this, because the lock is capped at the end of the broadcast.
  - Nothing records settings changes, so reveal-then-restore leaves no trail.
- **Why it matters:** a commissioner who is also a player can read every Curtain Call pick before lock, then submit their own. After a coast flip, any member can submit a pick they already know is right. A well-meaning commissioner can trigger the coast case by accident. A co-manager of the commissioner's team passes `is_league_commissioner` too.
- **Fix:** in `update_league_settings`, reject a change to either field if, for any active-season week without published results, `prediction_lock_at` is at or before `now()` under the old values or under the new values. Mirror that in the UI by disabling the Air Time and Pick 'Em Lock fields in the same case.
- **Evidence:** PGlite `attack1` T3: the commissioner couldn't see B's pick, set the lock to 100h and could read it (so could C), set it back to 0h, and submitted. T3b (rerun in `attack1b.out` after a timezone helper crash): on an east league after the East broadcast, submit was locked; after a coast flip to west, it succeeded. **3/3 upheld**, with the whole-league visibility, the end-of-broadcast cap on negative hours, and UI reachability added by verifiers.

**SEC-5 · `reset_draft` after the Season Clock lock reopens scoring settings and Grand Finale brackets** — Medium
- **Where:** [schema.sql:2343](../supabase/schema.sql#L2343) (`reset_draft`); [schema.sql:2716](../supabase/schema.sql#L2716) (`effective_hard_deadline_week`, roll-forward branch at [:2723](../supabase/schema.sql#L2723-L2734)); [schema.sql:1519](../supabase/schema.sql#L1519) (`update_scoring_categories` lock); [schema.sql:3037](../supabase/schema.sql#L3037) (`submit_grand_finale_prediction` lock); [schema.sql:2873](../supabase/schema.sql#L2873-L2886) (bracket SELECT policy).
- **What's wrong:** returning `draft_status` to `not_started` lets `effective_hard_deadline_week` roll forward, so `effective_grand_finale_deadline` moves back into the future.
- **Why it matters:** after every bracket has been visible league-wide, managers can resubmit, and the commissioner can change weights after real results. Peers' brackets are hidden again.
- **Fix:** have `reset_draft` refuse once `effective_grand_finale_deadline` has passed. Or freeze `judges_score_starts_week` to at least the current `effective_hard_deadline_week` on reset, and stop the roll-forward once a draft has ever completed (or store the passed deadline). If redrafting after the lock is meant to move the anchor, the Grand Finale deadline needs its own stored value.
- **Evidence:** PGlite `attack1` T5: before reset, both the weight change and B's resubmit were locked; after the commissioner's `reset_draft`, the deadline was in the future, the weight changed to 5, B resubmitted, and peers could no longer see B's bracket. **1/1 upheld**, line references confirmed. The verifier had to enable RLS by hand on `grand_finale_predictions` and `league_members` to reproduce the visibility half, because HEAD `schema.sql` doesn't (see SEC-12); live has RLS on.

**SEC-6 · Commissioner can open a late Grand Finale entry for themselves** — Medium
- **Where:** [schema.sql:2892](../supabase/schema.sql#L2892) (`unlock_grand_finale_late`); the UI offers it via `lateMissers` in [settings/page.tsx:251](../src/app/leagues/%5Bid%5D/settings/page.tsx#L251), which doesn't exclude the viewer.
- **What's wrong:** the RPC never checks that `p_manager_id` is a different team from the caller's, even though CLAUDE.md lists self-unlock as out. The commissioner sees an "Allow late" button on their own row.
- **Why it matters:** a commissioner who missed the deadline can read every peer's bracket, then submit their own at 100%.
- **Fix:** in the RPC, reject when `p_manager_id = resolve_acting_league_member(p_league_id)`, so a co-manager of the commissioner's team is covered too. Hiding the row in the UI is optional on top. Decide whether a super admin's exemption should apply only in leagues they are not a member of.
- **Evidence:** PGlite `attack1` T4: A unlocked A (`unlocked_by` = A, factor 1.00) and submitted after reading B's bracket. **1/1 upheld**; the verifier added the UI exposure.

**SEC-7 · A late Grand Finale entry is paid for an elimination that has aired but isn't published yet** — Medium
- **Where:** [schema.sql:3092](../supabase/schema.sql#L3088-L3096) (the `ineligible_couple_ids` snapshot in `submit_grand_finale_prediction`); [schema.sql:2956](../supabase/schema.sql#L2956-L2965) (`v_resolved` in the unlock); [settings/page.tsx:279](../src/app/leagues/%5Bid%5D/settings/page.tsx#L279) (`resolvedCount`); [grand-finale-late.ts:134](../src/lib/grand-finale-late.ts#L134-L138); [weekly-score-rows.ts:140](../src/lib/weekly-score-rows.ts#L140-L160).
- **What's wrong:** the snapshot of couples that "never pay" is built only from `couples.status` (eliminated / withdrawn / winner / runner_up / third_place), and that column only changes at official publish (`commit_episode_publication`, [schema.sql:3646](../supabase/schema.sql#L3646)). The unlock warning and the League Settings count read the same column. So a manager with an open late window can wait until a night airs and submit before the admin publishes. No drafted result is needed; the elimination is public on TV. The couple that just went home isn't snapshotted, and `eligibleGrandFinalePredictions` pays it in full on the next publish. This is separate from SEC-6: any legitimately unlocked late entrant can do it, and the commissioner gets no warning.
- **Why it matters:** the late entrant puts tonight's eliminated couple (two on a double week) in the exact first-out slot and collects points-per-correct × weight × `late_factor` per couple, which is exactly what the snapshot exists to prevent. Live publishes ran about 5–6 hours after the East air time for E04–E06, so the window is real. Live right now: 2 late windows are open and Grand Finale is on in all 5 leagues.
- **Fix:** refuse a late submit while any episode with a `week_id` has `airs_at <= now()` and no `results_published_at` ("Wait until Week N is published"), then snapshot by status as today. Treat that same state as "resolved" in `v_resolved` and the settings-page count. Checking `draft_episode_results` alone would miss the window before anything is drafted. Keep the warning generic ("a week has aired but isn't published") so it doesn't spoil a Spoiler-Free commissioner.
- **Evidence:** PGlite `gap1` section G2: week 1 aired 3 days earlier and was unpublished, with a drafted `eliminated` outcome for couple 306. The commissioner unlocked C with `p_acknowledge_resolved = false` and got no warning; C submitted with 306 at position 1; the unlock row then read `{late_factor 1.00, used true, ineligible_couple_ids []}`. Live read-only: `open_unlocks` = 2, `used` = 1, Grand Finale on in 5 of 5. **3/3 upheld.** Verifiers lowered it from High to Medium (needs a commissioner-opened, unused window; payoff bounded to one night's couples; the commissioner can Close the window first) and corrected the original "drafted elimination" framing: airing alone is enough.

**SEC-8 · Season Clock lock bypassed by pointing the Anchor Week at an unscheduled week** — Medium
- **Where:** [schema.sql:1520](../supabase/schema.sql#L1520) (the lock guard in `update_scoring_categories`); [schema.sql:268](../supabase/schema.sql#L268) (anchor only has to be > 0); [settings/actions.ts:227](../src/app/leagues/%5Bid%5D/settings/actions.ts#L227) (passed through unchanged); [schema.sql:2719](../supabase/schema.sql#L2719-L2740) and [:2749](../supabase/schema.sql#L2749-L2761) (where the null deadline comes from); compare [schema.sql:3041](../supabase/schema.sql#L3041) and [:2884](../supabase/schema.sql#L2884).
- **What's wrong:** the guard is `if not v_current.locking_exempt and v_deadline is not null and now() >= v_deadline`. `effective_grand_finale_deadline` returns null when the anchor week has no episodes. A commissioner can call the RPC directly (granted to `authenticated`) before the lock with anchor = 99; the deadline becomes null and the lock is skipped from then on. After results air, one save can change every weight and point value and move the anchor back to 1, which locks it again. The same holds during a draft, since `greatest(99, next unaired week)` is still 99, and `make_draft_pick`'s freeze ([schema.sql:2005](../supabase/schema.sql#L2005-L2015)) keeps 99. Elsewhere null is treated as locked: `submit_grand_finale_prediction` and the bracket RLS. This needs no `reset_draft`, unlike SEC-5.
- **Why it matters:** the lock exists so a commissioner never sees one category's real results before setting another's weight. With this, a commissioner leading in Curtain Call can watch week 1, raise the Curtain Call weight and lower Dance Card, and future publishes use those values. While the anchor is 99, peers' brackets are hidden, no bracket can be submitted, and a week published in that window pays 0 until republished; a careful commissioner restores the anchor before the next publish. Live exposure today is limited: 4 of 5 leagues are `locking_exempt` and the fifth is already past its lock. The risk is for new leagues and next season.
- **Fix:** in `update_scoring_categories`, also compute the deadline from the stored anchor (`v_current.judges_score_starts_week`) and treat the lock as passed if either the stored or the new anchor's week has aired. Or refuse a `p_judges_score_starts_week` with no `competition_weeks` row that has a scheduled episode in the active season. At minimum, treat a null deadline as locked, as the other callers do.
- **Evidence:** PGlite `gap1` section G1: draft complete, anchor 1. Before week 1, A set the anchor to 99 and the deadline read null. After week 1 aired, the same RPC returned `{judges_score_starts_week: 1, judges_score_category_weight: 5}`, and a further change then raised "Scoring settings are locked for the season". Live read-only: leagues = 5, `locking_exempt` = 4. **1/1 upheld**; the verifier added the during-draft and `make_draft_pick` paths.

**SEC-9 · `startCorrection` has no published-episode guard** — Low
- **Where:** [results-draft.ts:349](../src/lib/results-draft.ts#L349-L372) (calls `deleteAllDraftRows` at [:288](../src/lib/results-draft.ts#L288-L297)); [actions.ts:171](../src/app/admin/results/actions.ts#L171-L178).
- **What's wrong:** `startEpisodeCorrection` (propose tier) calls `startCorrection`, which deletes every draft row and every `draft_couple_releases` row for the episode and reseeds from live tables, without checking `results_published_at`. The UI only calls it for published episodes with no draft ([results-form.tsx:396](../src/components/results-form.tsx#L396-L405)), but the action accepts any episode id. The comment at [:344](../src/lib/results-draft.ts#L344-L348) says the caller confirms; the UI never does.
- **Why it matters:** called on tonight's unpublished episode, it erases every couple's entered scores and releases in one call. It adds no new privilege, though: the same propose tier can already wipe a night couple by couple through `saveEpisodeDraft` with empty dances and `withdrawDraftCoupleAction`. Live tables are never written on this path.
- **Fix:** select `results_published_at` in `startCorrection`'s episode read and return an error when it is null, matching `releaseDraftCouple`'s own check at [:311](../src/lib/results-draft.ts#L311-L317). Fix the stale comment.
- **Evidence:** code read of the lines above. **3/3 upheld**, and all three lowered it from High to Low as hardening, since the same wipe is already reachable at the same tier.

**SEC-10 · A co-manager can also join the same league as a primary, and their actions land on an arbitrary team** — Low
- **Where:** [schema.sql:868](../supabase/schema.sql#L868) (`join_league`); [schema.sql:1325](../supabase/schema.sql#L1325) (`resolve_acting_league_member`); [apply-draft-safety.sql:6](../supabase/apply-draft-safety.sql#L6) (also redefines `join_league` without the check).
- **What's wrong:** `join_league` doesn't check whether the caller is already a co-manager in that league (`join_as_co_manager` checks the reverse). `resolve_acting_league_member` then uses `limit 1` with no `ORDER BY`, so which team wins depends on physical row order.
- **Why it matters:** the member's own new team is silently unreachable: draft picks, queue and predictions all resolve to the other team. Controlling two teams is already possible with a second account, so this isn't an escalation, and the member can still leave (`remove_co_manager` then `leave_league`, or a commissioner removal).
- **Fix:** in `join_league`, raise when a row exists with `co_manager_id = auth.uid()` for that league; update both definitions. Optionally make the resolver deterministic (prefer the `user_id = auth.uid()` row).
- **Evidence:** PGlite `attack1` T2: F joined as B's co-manager, then via the league code, and ended up with two rows; the resolver returned B and F's prediction landed on B's team. **1/1 upheld.** The verifier lowered it from Medium to Low and corrected the original "cannot leave" claim (`remove_co_manager` plus `leave_league` works).

**SEC-11 · Live `anon`/`authenticated` hold TRUNCATE, REFERENCES, TRIGGER and MAINTAIN on every table; stale backup tables remain** — Low
- **Where:** [schema.sql:11](../supabase/schema.sql#L11) (where the fix belongs, next to the `service_role` grant).
- **What's wrong:** every live public table's `relacl` includes `anon=Dxtm` and `authenticated=(r)Dxtm`. These come from Supabase's platform default privileges for owner `postgres` (with "Automatically expose new tables" off, only `arwd` is withheld), not from `schema.sql`. The `_backup_20260918_*` tables also remain.
- **Why it matters:** PostgREST can't reach these privileges today, but any future path that gives these roles SQL access would bypass RLS.
- **Fix:** after line 12, add `revoke truncate, references, trigger, maintain on all tables in schema public from anon, authenticated;` and `alter default privileges for role postgres in schema public revoke truncate, references, trigger, maintain on tables from anon, authenticated;`. `MAINTAIN` needs PG17 (live is 17.6), so the PGlite tests may need that keyword guarded. Drop the backup tables (RLS on, no SELECT grant, so no data is exposed today) and regenerate `types.ts`.
- **Evidence:** live `has_table_privilege` and `relacl` query, plus the live default ACL (`postgres/r = anon=Dxtm, authenticated=Dxtm`). **1/1 upheld**; the verifier identified the platform default as the root cause.

**SEC-12 · `schema.sql` does not enable RLS on its own** — Low
- **Where:** [schema.sql:2469](../supabase/schema.sql#L2469) (the only `enable row level security`, for `draft_couple_releases`).
- **What's wrong:** every other table relies on the live project's `ensure_rls` event trigger, which calls `rls_auto_enable`. A few `apply-*.sql` files enable RLS explicitly (`apply-draft-queue.sql:19`, `apply-episode-guest-judges.sql:15`, `apply-grand-finale-late-unlock.sql:19`); `schema.sql` doesn't.
- **Why it matters:** applying `schema.sql` to a fresh or rebuilt project without that trigger would serve granted tables unfiltered, including peers' pre-lock predictions and every profile. Live has RLS on 39 of 39 public tables, so there's no exposure today.
- **Fix:** add `alter table public.<t> enable row level security;` next to each table, or one closing `DO` block that enables it on every public table. Both are idempotent and safe on live.
- **Evidence:** grep finds the single enable; the live-only `rls_auto_enable` function shows the dependency. **1/1 upheld**, confirmed in PGlite and read-only against live. Two other verifiers ran into the same gap independently (SEC-5, SEC-14).

**SEC-13 · `reject_waiver_claim` can reject an already-approved claim** — Low
- **Where:** [schema.sql:3349](../supabase/schema.sql#L3349).
- **What's wrong:** no pending-status check and no `FOR UPDATE` lock, so an approved claim (including an auto-approved FCFS claim) is marked rejected while the roster swap stays.
- **Why it matters:** the claim history no longer matches the roster. Only the league's own commissioner can trigger it: a stale second tab, an approve/reject race, or a direct RPC call.
- **Fix:** mirror `approve_waiver_claim`: `select … for update`, then raise "This recast has already been resolved" when the status isn't `pending`. Or add `and status = 'pending'` to the `UPDATE` and raise if no row changed.
- **Evidence:** PGlite `attack2`: after approve then reject, the status read rejected but the waiver roster row was still there. The live function body matches HEAD. **1/1 upheld.**

**SEC-14 · Fellow members can read each other's `is_super_admin` and `deletion_requested_at`** — Low
- **Where:** [schema.sql:726](../supabase/schema.sql#L726) (table-wide SELECT on `profiles`); [schema.sql:1377](../supabase/schema.sql#L1377) (fellow-member policy).
- **What's wrong:** any fellow member can read every `profiles` column for their league-mates, including `is_super_admin`, `deletion_requested_at`, `spoiler_free_mode` and `created_at`.
- **Why it matters:** a minor privacy leak, mainly who has asked to delete their account and who the super admin is.
- **Fix:** column grants apply to every row, including your own, so revoking these columns would break the app's own-row reads ([settings/page.tsx:48](../src/app/leagues/%5Bid%5D/settings/page.tsx#L48), account settings, `src/lib/account-deletions.ts`, `requireAdminAccess` at [actions.ts:36](../src/app/admin/results/actions.ts#L36)). Instead grant `SELECT` only on `id`, `display_name`, `avatar_url` (and `spoiler_free_mode` unless that moves too), and serve the viewer's own private flags through a `SECURITY DEFINER` self-profile RPC.
- **Evidence:** PGlite `attack2`: B read C's deletion flag. **1/1 upheld**; the verifier rewrote the fix to keep own-row reads working.

**SEC-15 · League invite code can't be rotated, so removed members can rejoin** — Low
- **Where:** [schema.sql:868](../supabase/schema.sql#L868) (`join_league`); also `create_league`'s code insert at [:821](../supabase/schema.sql#L821-L824) and `remove_league_member` at [:1137](../supabase/schema.sql#L1137).
- **What's wrong:** nothing ever updates `leagues.invite_code`, and `join_league` has no ban check; removal leaves no record.
- **Why it matters:** a removed member can rejoin straight away, and a leaked code is permanent.
- **Fix:** add a commissioner-only, schema-qualified RPC behind `is_league_commissioner` that regenerates the code. Optionally record removed members and have `join_league` refuse them.
- **Evidence:** `git grep` shows `invite_code` is only written in `create_league`. Live: no rotate function and no `UPDATE` grant on `leagues` for `authenticated`. **1/1 upheld.**

**SEC-16 · Password change needs no reauthentication; the pick clock accepts any value** — Low
- **Where:** [account/actions.ts:19](../src/app/settings/account/actions.ts#L19) (`updatePassword`); [schema.sql:107](../supabase/schema.sql#L107) (the `pick_time_limit_seconds` column) and [:1432](../supabase/schema.sql#L1432) (unchecked assignment in `update_league_settings`).
- **What's wrong:**
  - `updatePassword` works on the session alone. Live `security_update_password_require_reauthentication` is false, as are require-current-password and the password-changed notification email.
  - `update_league_settings` accepts any `pick_time_limit_seconds`: -5, 0 and 1–9 all succeed. The ≥10 rule exists only in the client ([league-modules-form.tsx:459](../src/components/league-modules-form.tsx#L459), and only when Dance Card is on). It can also change mid-draft.
- **Why it matters:** a borrowed session can change the password and lock the owner out. A commissioner can set a clock that makes every turn immediately auto-pickable.
- **Fix:** enable reauthentication (it only demands a nonce for sessions older than about 24h), so also turn on require-current-password and the password-changed email, and send the current password from the settings form. Add `CHECK (pick_time_limit_seconds >= 10)` to match the client floor and reject lower values in the RPC.
- **Evidence:** live auth config; PGlite `attack2`. **1/1 upheld**; the verifier widened the clock problem from negative values to anything under 10 and added the extra auth settings.

**SEC-17 · No range validation on judge scores anywhere, so a typo is released to fans and can be published** — Low
- **Where:** [results-draft.ts:105](../src/lib/results-draft.ts#L105-L193) (`saveDraftResults`); [results-form.tsx:488](../src/components/results-form.tsx#L488) (`Number(v)`) and the free-text inputs at [:831](../src/components/results-form.tsx#L831-L835); [schema.sql:558](../supabase/schema.sql#L558) (`judge_scores.score`), [:2446](../supabase/schema.sql#L2446) (`draft_judge_scores.score`), [:586](../supabase/schema.sql#L586) and [:2484](../supabase/schema.sql#L2484) (`bonus_points`).
- **What's wrong:** judge score boxes are free-text inputs. `saveDraftResults` (service-role client) inserts whatever arrives, and so does `commit_episode_publication`. No column has a range `CHECK`; the only CHECKs on the dance, judge and result tables are the outcome enums. Non-numeric input already fails, because `NaN` serializes to null and hits `NOT NULL`.
- **Why it matters:** a commissioner at the ET broadcast types 77 instead of 7 and taps Save as Draft Score. Fans who chose Stay Updated or Mark Watched see a 77+ total, and judges-only standings move. If an admin then taps per-couple Publish, `recomputeWeekForReveal` writes it into `weekly_manager_scores` for every league. The impact is softened: draft rows are read live, so fixing the typo corrects what fans see on the next autosave; released drafts are labeled Unverified; and the card shows the dance total beside the boxes before an admin publishes. A rogue propose-tier user (SEC-20) can post out-of-range values on purpose.
- **Fix:** add `CHECK (score between 0 and 10)` on `judge_scores` and `draft_judge_scores` (first confirm no historical row is outside that range), validate in `saveDraftResults`, and add `inputMode="numeric"` with min/max on the score input. `bonus_points` needs a product decision first: negative values may be intended as penalties, and bonus never shows in released drafts (it only matters on publish through Finish Week).
- **Evidence:** code read of the lines above. PGlite `gap2`: `pg_constraint` shows only the outcome-enum CHECKs; inserting `draft_judge_scores.score = 77` and `draft_episode_results.bonus_points = -500` both succeeded. **1/1 upheld.** The verifier lowered it from Medium to Low and corrected the bonus part, which the original overstated.

**SEC-18 · Live auth auto-confirms email sign-ups with no captcha, a 6-character password minimum and no leaked-password check** — Low
- **Where:** the live Supabase Auth config; the code path that relies on it is `signUp` at [actions.ts:31](../src/app/auth/actions.ts#L31-L50).
- **What's wrong:** live `mailer_autoconfirm` = true, `security_captcha_enabled` = false, `password_min_length` = 6, `password_hibp_enabled` = false, with email and Google sign-up both on. Anyone can create a confirmed account for an email they don't own, and script unlimited accounts.
- **Why it matters:**
  - Email squatting and impersonation: an attacker registers a league-mate's address with a matching display name and joins with a leaked invite code. The real owner's later password sign-up fails with "already registered", and there's no self-serve reset to recover (ux-audit A1, still open), which makes squatting harder to undo.
  - Unlimited scripted accounts multiply guessing against the league and co-manager code spaces (ux-audit A3, SEC-2).
  - Weak, unchecked passwords.
- **Fix:** captcha (Turnstile or hCaptcha) on sign-up plus HIBP is the lower-friction first step. Raise `password_min_length` to 8+ and update the client `minLength={6}` at [sign-up/page.tsx:37](../src/app/sign-up/page.tsx#L37) and [account-data-form.tsx:76](../src/components/account-data-form.tsx#L76) and `:87`. Turning off `mailer_autoconfirm` also needs `signUp` to handle a null session with a "check your email" state (today it redirects into the app, which bounces a sessionless user to sign-in) and working auth email (the default SMTP allows 2 per hour, and A1 notes delivery isn't confirmed).
- **Evidence:** read-only Management API `GET /config/auth` (non-secret keys); code read of `signUp`. **1/1 upheld.** The verifier removed the original claim that this amplifies the propose tier (one account already gets it, by design; see SEC-20) and corrected the password-reset recovery path, which doesn't exist yet. Whether a later Google sign-in merges into the squatter's account is untested (see Limits).

**SEC-19 · Display names and league names have no length limit at the database** — Low
- **Where:** [schema.sql:727](../supabase/schema.sql#L727) (`grant update (display_name, avatar_url) on public.profiles`); the column at [:22](../supabase/schema.sql#L22); `create_league` at [:780](../supabase/schema.sql#L780) and `rename_league`'s blank-only check at [:1237](../supabase/schema.sql#L1237); `handle_new_user` at [:698](../supabase/schema.sql#L698-L706); [profile/actions.ts:6](../src/app/settings/profile/actions.ts#L6).
- **What's wrong:** `display_name` is user-writable with no length `CHECK`. `create_league` and `rename_league` only reject blank names. `handle_new_user` copies `display_name` / `full_name` from sign-up metadata verbatim. `updateProfile`'s trim and "Display name is required" check are UX only: a user can `PATCH /rest/v1/profiles` directly with their JWT and set a 200,000-character name, or an empty one.
- **Why it matters:** one member's huge name ships in every league-mate's Standings, Picks, roster cards, Score History, switcher payload and Realtime `league_members` events, bloating every page load for that league and breaking layouts. A huge league name does the same on the anon-callable invite preview and Home cards.
- **Fix:** add `CHECK (char_length(btrim(display_name)) between 1 and 40)` on `profiles` and `CHECK (char_length(btrim(name)) between 1 and 60)` on `leagues` (live max `display_name` today is 38). Truncate with `left(…)` in `handle_new_user`, or sign-ups fail when a Google `full_name` is too long. Mirror the limits in `updateProfile` and the create/rename forms.
- **Evidence:** PGlite `gap1` section G3: as B, a direct `update` set a 200,000-character display name; as X, `create_league` accepted a 200,000-character name; fellow member C read both. **1/1 upheld**; the verifier added the empty-name case and the `left()` caveat.

**SEC-20 · Propose tier is self-service: creating a league grants results drafting and release** — High
- **Settled decision:** "Results entry has three access tiers" (Propose = commissioner of any league), and per-couple Draft Scores at propose tier, season-wide.
- **Where:** [actions.ts:46](../src/app/admin/results/actions.ts#L46-L54) (`requireProposeAccess`); [schema.sql:780](../supabase/schema.sql#L780) (`create_league`, granted to `authenticated` at [:1284](../supabase/schema.sql#L1284)); [results.ts:13](../src/lib/results.ts#L13-L24); [results-draft.ts:105](../src/lib/results-draft.ts#L105-L193) (`saveDraftResults`); `removeEpisodeCustomMoment` at [actions.ts:103](../src/app/admin/results/actions.ts#L103) and `removeDraftCustomMoment` at [results-draft.ts:255](../src/lib/results-draft.ts#L255); [results-reveal.ts:72](../src/lib/results-reveal.ts#L72-L83).
- **What's wrong:** `requireProposeAccess` allows any commissioner of any league. `create_league` makes the caller a commissioner in one call, and sign-ups auto-confirm with no captcha (email or Google). So any new account can, season-wide:
  - overwrite real draft entries, release or withdraw any couple, and delete draft custom moments (`removeDraftCustomMoment` isn't scoped by episode);
  - wipe tonight's whole draft and every release in one call through `startEpisodeCorrection`, which has no published-episode guard (SEC-9), or couple by couple through empty saves and withdraws;
  - save unbounded judge scores and bonus points (SEC-17). `revealCouple` copies whatever the draft holds at the moment an admin taps Publish.
- **Why it matters:** a stranger can disrupt a live night, show fans fake Unverified scores, or get altered values posted if an admin publishes without re-checking.
- **Fix, if wanted:** grant propose access through an explicit flag or an admin-approved commissioner list rather than league creation. Independent of that decision and worth doing either way: the published-episode guard in `startCorrection` (SEC-9), score bounds (SEC-17), and scoping `removeDraftCustomMoment` by `episode_id`.
- **Evidence:** code read of the lines above; live auth config (sign-ups open, `mailer_autoconfirm` true, captcha off, Google on) by read-only Management API `GET`. PGlite repro of the propose path by a verifier. **3/3 upheld**, all three flagging the conflict. The verifiers added `startCorrection` as the strongest live-night impact and the line corrections above. They split on whether that wipe is new: the SEC-9 verifiers note the same wipe is already possible couple by couple, so it's listed there as hardening.

## Checked and held up

- Every public function runs with `search_path` set to empty on live. Only `league_invite_preview` can be called by `anon` (`handle_new_user` and `rls_auto_enable` are trigger types and errored without effect).
- `episode_publication_snapshot` and `commit_episode_publication` are denied to `anon` and `authenticated`, in PGlite and on live.
- `draft_*` tables are denied to `authenticated`. `visible_draft_dance_scores` returns only couples that were released and unlocked by the viewer.
- Column grants block direct updates of `is_super_admin` and `deletion_requested_at`. The `judges_score_multiplier` lock after draft completion and the Season Clock weight lock both hold (apart from the bypasses in SEC-5 and SEC-8).
- Peers' predictions and brackets stay hidden before lock. Cross-league draft, waiver, settings and member actions are all refused. `record_draft_pick` and `finalize_waiver_claim` can't be called directly.
- A throwaway account sees 0 rows of every real league table.
- `league_invite_preview` returns only name, team count and draft state. It uses an exact indexed lookup, and with 5 leagues it takes roughly 177M guesses per hit (extends ux-audit A3).
- `RESULTS_ENTRY_OPEN_TO_ALL` has no reader at HEAD (removed in `384f78d`). It is still set in `.env.local`.
- `safeRelativePath` blocked every vector that changes the origin.
- Every live public function body matches its HEAD `schema.sql` definition, except a cosmetic message in `finalize_waiver_claim` ("Waiver claim not found" vs "Recast not found"). No `apply-*.sql` leftovers (`undo_last_auto_pick`, `_sp_*`) exist live.
- Live RLS policies match `schema.sql` one-to-one (32 and 32). The only differences are two names truncated at 63 characters. The only non-SELECT policy is the `profiles` owner UPDATE, which is backed by column grants.
- Live `EXECUTE` privileges: `anon` can execute only `league_invite_preview`, plus the trigger-type `handle_new_user` and `rls_auto_enable`, which can't be invoked. `record_draft_pick` and `finalize_waiver_claim` aren't executable by `authenticated`. The publication RPCs are `service_role` only.
- Every `?from=` and `?next=` consumer (settings pages, draft/settings/waivers `closeHref`, auth actions, the `/auth/callback` route) goes through `safeRelativePath`.
- Pages using the service role are gated: `/admin/accounts` and its action check `is_super_admin`, and `SuperAdminManagers` on League Settings renders only after an `is_super_admin` check. The only ungated one is `loadResultsPageData` on Scores/Schedule, which is SEC-3.
- Every non-admin server action delegates to an RPC that does its own `auth.uid()` check, or reads through the viewer's RLS-scoped client (`getScoreHistory`; `getSwitcherSummaries`, which takes league ids from the viewer's memberships; `getSpoilerProgress`).
- Realtime (live, throwaway accounts): a non-member subscribed to `league_members` receives no events from another league.
- Live auth config has anonymous sign-ins disabled (`external_anonymous_users_enabled` = false) and secure email change enabled.
- Avatar URLs aren't rendered anywhere, so the user-writable `avatar_url` column isn't an image or tracking vector today.
