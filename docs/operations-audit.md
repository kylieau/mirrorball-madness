# Operations audit — 2026-10-17

A read-only review of how the app runs in production: auth and redirect config, backups and recovery, schema rebuildability, error handling and observability, live-night load, the publish and reveal paths, the iOS wrapper, dependencies and response headers. Nothing in the app was changed: no app code, schema, config or data. The only new file is this report. Every finding below was re-checked by one to three independent verifiers, and their corrections are folded into the text. Several findings overlap `docs/security-audit.md` (untracked in the working tree at the time of writing); those are cross-referenced by SEC number rather than repeated.

**Limits**
- The Management API's read-only SQL role can't `SET ROLE authenticated`, so the live per-row cost of the `predictions` and `grand_finale_predictions` RLS policies wasn't measured. The performance advisor flagged `auth_rls_initplan` on 7 policies and 46 unindexed foreign keys, which is immaterial at 16 MB and 5 leagues.
- Update Email (OPS-21) couldn't be reproduced end to end: `.example.test` addresses are rejected before any send, and only `example.test` throwaways are allowed.
- The Google auto-link takeover (OPS-3) was shown from existing account shapes, not by doing a Google sign-in. No OAuth browser flow is available here.
- Vercel is unchecked: no CLI, token or `.vercel` link. Plan, `maxDuration`, log retention, and whether preview deployments (allowed by the `*.vercel.app` redirect patterns) share the production Supabase project and service-role key are all unverified.
- Whether Supabase's per-IP auth rate limits (`rate_limit_token_refresh` 150 per 5 minutes) bite when server-side refreshes come from shared Vercel IPs wasn't measured. There's no edge-log access.
- The draft pick clock is client-driven (any open draft room or Picks card fires `make_auto_draft_pick`). BACKLOG.md:195 already documents this, so it isn't reported.
- No iOS device run.

Severity:
- **High:** a real user or attacker can break scoring, see spoilers/peer picks/unreleased scores early, write to data they shouldn't, lose data, or take the site down on a live night.
- **Medium:** wrong behavior or real risk on a common path, or a likely live-night failure with a workaround.
- **Low:** hardening, polish, maintainability with a concrete payoff.

## Findings

**OPS-1 · Auth redirect allow-list accepts any `*.vercel.app/auth/callback`, so a phishing link or a requested magic link can take over an account** — High
- **Where:** the live Supabase Auth URL Configuration (`uri_allow_list`), not a repo file. Code anchors, where the app builds its own legitimate redirect: [actions.ts:63](../src/app/auth/actions.ts#L63), [actions.ts:40](../src/app/auth/actions.ts#L40), [google-sign-in-button.tsx:15](../src/components/google-sign-in-button.tsx#L15). Same issue as SEC-1 in `docs/security-audit.md`.
- **What's wrong:**
  - The allow-list contains `https://*.vercel.app/auth/callback`. Anyone can deploy on vercel.app, so GoTrue accepts an attacker's own `/auth/callback` as `redirect_to` for OAuth and every email link. (The wildcard is path-scoped: `https://x.vercel.app/other/path` falls back to `site_url`. That doesn't help, since the attacker controls their own callback path.)
  - It also contains `https://mirrorball-*-madness-kylie8.vercel.app`, both bare and with `/**`. That host pattern can be claimed: `https://mirrorball-x-madness-kylie8.vercel.app` returns `DEPLOYMENT_NOT_FOUND`, so any Vercel user who names a project to fit gets a matching host, with no path restriction.
  - Dead entries remain: `dwts-fantasy-app-kylie8` (410), `dwts-fantasy-app-six` (404) and the retired `com.kylieau.dwtsfantasy://` scheme.
- **Why it matters:**
  - OAuth: the attacker sends `https://wssbwgtsejamlbvfofvu.supabase.co/auth/v1/authorize?provider=google&redirect_to=https://evil-anything.vercel.app/auth/callback` with their own PKCE `code_challenge`. The victim completes Google sign-in, which Google often auto-approves, GoTrue sends the code to the attacker's host, and the attacker exchanges it with their verifier for the victim's session and refresh token.
  - Email, likely the stronger vector: email sign-in is enabled, so the attacker can `POST /auth/v1/otp` with the victim's email and that `redirect_to`. The victim gets a genuine magic-link email from the app; clicking it sends their session to the attacker. No crafted URL is needed. Sign-up confirmations and password-reset emails are exposed the same way.
  - With the session the attacker acts as the victim: changes picks, or, if the victim is the super admin, publishes or undoes results.
- **Fix:** in Supabase Auth → URL Configuration, remove `https://*.vercel.app/auth/callback`, both `mirrorball-*-madness-kylie8` entries, and the dead hosts and old scheme. Allow only the exact production hosts with `/**` (`https://mirrorball-madness-kylie8.vercel.app/**`, `https://dwts-fantasy-mirrorball-madness.vercel.app/**`), the native `com.kylieau.mirrorballmadness://auth/callback`, and localhost for dev. If preview deploys need sign-in, use Vercel's per-project preview domain behind deployment protection, not a `*.vercel.app` glob. This one change closes the OAuth, magic-link, confirmation and reset paths together.
- **Evidence:**
  - Read-only `GET /config/auth` returned `uri_allow_list` = localhost entries, `https://dwts-fantasy-app-kylie8.vercel.app/(**)`, `https://dwts-fantasy-app-six.vercel.app`, `com.kylieau.dwtsfantasy://auth/callback`, `com.kylieau.mirrorballmadness://auth/callback`, `https://mirrorball-madness-kylie8.vercel.app/(**)`, `https://mirrorball-*-madness-kylie8.vercel.app(/**)`, `https://dwts-fantasy-mirrorball-madness.vercel.app/auth/callback`, `https://*.vercel.app/auth/callback`.
  - Throwaway-account probe (`admin.generateLink` magic link, no email sent, then `deleteUser`): GoTrue kept `redirect_to=https://audit-probe-not-ours.vercel.app/auth/callback` and `https://mirrorball-x-madness-kylie8.vercel.app/auth/callback` as given, but replaced `https://evil.example.com/auth/callback` with `site_url`. So the allow-list is what lets the vercel.app hosts through.
  - A verifier reproduced the same check without any account, using bogus-token `GET /auth/v1/verify`: the 303 `Location` is `redirect_to` when it passes the allow-list and `site_url` when it doesn't. The `/otp` vector wasn't run, since it would email a real address.
  - Curl to `https://mirrorball-x-madness-kylie8.vercel.app/` returned 404 `x-vercel-error: DEPLOYMENT_NOT_FOUND`.
  - Verifiers: 3/3 upheld. They noted the root cause is dashboard config and the cited lines are anchors only.

**OPS-2 · Scores and Schedule pages send every episode's draft (unreleased dances and pre-publish outcomes) to any signed-in user** — High
- **Where:** [results-page-data.ts:180](../src/lib/results-page-data.ts#L180); [results/page.tsx:73](../src/app/admin/results/page.tsx#L73); [schedule/page.tsx:35](../src/app/admin/schedule/page.tsx#L35); `loadDraftForEpisode` at [results-draft.ts:196](../src/lib/results-draft.ts#L196). Same issue as SEC-3.
- **What's wrong:**
  - `loadResultsPageData` uses the service-role client to call `loadDraftForEpisode(admin, e.id)` for every episode: draft dances with per-judge scores, draft outcomes (eliminated, saved by judges, immunity, bonus) and In Jeopardy.
  - `/admin/results` (Scores, View tier) and `/admin/schedule` pass the whole `draftsByEpisode` to `"use client"` components (`ResultsScreen` → `AllResultsView`, `ScheduleManager`), so it's serialized into the page HTML/RSC payload for any signed-in user, with no propose or admin check.
  - Neither page needs it. Schedule reads only `dances[].coupleId` ([schedule-manager.tsx:439](../src/components/schedule-manager.tsx#L439)) and `hasDraft` (`:454`). Scores reads `hasDraft` ([all-results-view.tsx:216](../src/components/all-results-view.tsx#L216)) and `entries.length` (`:259`, `:373`).
  - This bypasses `visible_draft_dance_scores()` / `draft_couple_releases` and the Spoiler-Free gate, contradicting CLAUDE.md's "only released couples' dances are ever readable".
- **Why it matters:**
  - Today every draft row is a correction draft for an already-published episode, whose live rows any signed-in user can already read, so nothing extra is exposed yet.
  - The exposure starts with E07 (2026-10-20, 8pm ET). While commissioners enter per-couple dances during the East broadcast, and once outcomes are ticked on Finish Week, any league member can open `/admin/schedule` or `/admin/results` and read unreleased scores and who is marked eliminated in the page source, hours before West Coast viewers watch.
  - Outcomes reach the draft through the ordinary per-edit autosave (`results-form.tsx` `setStatus` → `updateRow` → `scheduleAutosave`, around lines 651–662, writing `draft_episode_results.outcome`), not only at Finish Week submit. So the window runs from the first outcome tick until publish.
  - The page's on-screen spoiler cutoff doesn't filter the payload.
- **Fix:** for Scores and Schedule, compute only what they render on the server (`hasDraft` per episode, drafted couple ids, entry counts) and never pass the full `DraftState`. Load full drafts only on `/admin/results/enter`, after the existing `requireProposeAccess` check, either through a flag on `loadResultsPageData` or a separate loader. The View tier stays open; it just stops carrying draft contents.
- **Evidence:**
  - Code: `results-page-data.ts:180-183` builds `draftsByEpisode` with the admin client. `admin/results/page.tsx:40` and `:73`, and `admin/schedule/page.tsx:24` and `:35`, pass it to client components (`results-screen.tsx:1`, `schedule-manager.tsx:1`).
  - Live: a brand-new throwaway account with no leagues, signed in via `@supabase/ssr` cookies, made plain HTML GETs of `https://mirrorball-madness-kylie8.vercel.app/admin/schedule` and `/admin/results` with no client JS. Both returned 200 with `draftsByEpisode` embedded: Schedule had 58 `judgeScores` keys and 5 `"outcome":"eliminated"`; Results had 59 and 11. The sample included a full draft dance with judge ids, song title and score. One verifier re-ran this on 2026-10-19 against production and got the same counts.
  - Read-only SQL: draft rows exist only on published episodes E01 and E03–E06, none on E07–E12.
  - Verifiers: 3/3 upheld. One argued for Medium: anyone can call `create_league`, become a commissioner and open Enter Results, where every draft is shown by design. That's the propose tier being self-service (SEC-20, filed under "Conflicts with settled decisions" in the security audit). This fix stops the leak to non-commissioners but doesn't change that wider exposure.

**OPS-3 · Email sign-up is auto-confirmed and Google sign-in auto-links into an existing password account, so whoever registers a victim's email first keeps password access** — High
- **Where:** [actions.ts:35](../src/app/auth/actions.ts#L35) (`signUp`), [actions.ts:53](../src/app/auth/actions.ts#L53) (`signInWithGoogle`), plus live Auth config. Extends SEC-18 and resolves the open item in that audit's Limits.
- **What's wrong:**
  - `signUp` creates an email/password account for any address. Auth config has `mailer_autoconfirm: true`, so the user row's `email_confirmed_at` is set the moment the account is created and ownership of the address is never proven.
  - Google is enabled. GoTrue links a verified Google identity onto an existing user with the same email when that user row is confirmed. Here the row is confirmed by auto-confirm, so the link happens, and GoTrue's `RemoveUnconfirmedIdentities` step (which would strip the password) is skipped. On all 4 linked live accounts the email identity's own `identity_data.email_verified` is `false`; user-level confirmation is what decides it.
  - This happens on this project: 4 of 58 live accounts have an `email` identity created first and a `google` identity added later (0 to 2.9 days later), and on each the email was confirmed 0.0–0.2 seconds after sign-up, which is auto-confirm, not a clicked link.
  - No hook mitigates it: `hook_before_user_created_enabled` and `hook_custom_access_token_enabled` are both false.
- **Why it matters:** an attacker who knows a friend's email signs up with it and a password of their choosing. This works whenever the address isn't registered yet, which is typical when a commissioner shares an invite link in a group chat. When the real person later taps Continue with Google, they land in the attacker's account and build their league life there. The attacker can still sign in with the password: see the victim's picks before lock, change their Curtain Call and Grand Finale picks, draft for them, or request account deletion.
- **Fix:**
  - Once SMTP is connected (already a BACKLOG prerequisite for forgot password), turn on Confirm email (`mailer_autoconfirm: false`). GoTrue still links Google onto an unconfirmed password user, but then clears that password, so the attacker loses access. `signUp` also needs to handle a null session with a "check your email" state (see SEC-18's fix).
  - That only protects accounts created after the switch; existing auto-confirmed password accounts stay linkable. Until then, either disable email/password sign-up and keep Google only, or add a custom access-token hook that refuses or flags an OAuth sign-in landing on an email identity that was never confirmed by link.
  - Prompt the 4 accounts that already have both identities (and future linkers) to reset their password.
- **Evidence:**
  - Read-only `GET /config/auth`, non-secret fields only: `mailer_autoconfirm` true, `external_email_enabled` true, `external_google_enabled` true, `security_manual_linking_enabled` false, `smtp_host` null.
  - Read-only service-role `listUsers` plus `getUserById` over all 58 users, counts only, no emails printed: providers per user were email 47, google 7, email+google 4. For all 4 linked users the email identity predates the google identity, and `email_confirmed_at` was 0.0–0.2s after `created_at`.
  - The retained password is inferred from the surviving email identity and GoTrue's behavior (`RemoveUnconfirmedIdentities` runs only for unconfirmed users), not observed: `encrypted_password` is in the `auth` schema, outside read scope. The end-to-end takeover wasn't run, since it needs a real Google account.
  - Code: `actions.ts:31-50` (sign-up with no confirmation gate, redirecting straight in) and `:53-74` (Google OAuth).
  - Verifiers: 3/3 upheld, with the mechanism and fix corrections above folded in.

**OPS-4 · No database backups exist (Free plan, PITR off) and there's no restore plan, so a deleted league or a bad hand-run SQL script can't be undone** — Medium
- **Where:** `delete_league` at [schema.sql:1260](../supabase/schema.sql#L1260); the `deleteLeague` action at [settings/actions.ts:26](<../src/app/leagues/[id]/settings/actions.ts#L26>); the project's backup settings.
- **What's wrong:**
  - The org is on the Free plan. The backup list is empty and PITR is off (`walg_enabled: true` doesn't mean there's anything to restore from).
  - No document in the repo describes a restore path, `pg_dump` routine or export. The only in-database safety net is three ad hoc `_backup_20260918_*` tables in the same database, not in `schema.sql`.
  - Fixes run as hand-applied `supabase/apply-*.sql` files in the SQL editor.
  - `delete_league` is a plain `delete from public.leagues` that cascades to every league-keyed table. The UI makes the commissioner type the league name exactly first ([league-info-section.tsx:163](../src/components/league-info-section.tsx#L163)), so it isn't a mis-tap risk. But the RPC has no such guard, and anyone who passes `is_league_commissioner` can call it, including a promoted co-commissioner and the co-manager on a commissioner's team.
- **Why it matters:** a regretted or malicious league delete, a bad `apply-*.sql` (a rescale or recompute script with a wrong `WHERE`), or an accidental truncate in the dashboard permanently loses picks, brackets, rosters and standings. A wrong scores publish is recoverable through correction mode; lost data isn't. Separately, the Free plan pauses inactive projects, which causes downtime (not data loss) over the long off-season, since leagues persist across seasons.
- **Fix:** move to Pro for daily backups (add PITR if wanted), or at minimum schedule a `pg_dump` (schema and data) to storage you control, for example a weekly GitHub Action plus one before each live night and before any `apply-*.sql`. Document the restore steps in CLAUDE.md or a runbook. Consider soft-deleting leagues (`archived_at`, purge later) so a regretted delete can be reversed. Before the off-season, either upgrade or keep a recent dump.
- **Evidence:** read-only Management API: `GET /v1/organizations/wqoptsldbfonozszqkxn` returned plan `"free"`; `GET /projects/wssbwgtsejamlbvfofvu/database/backups` returned `{pitr_enabled: false, walg_enabled: true, backups: []}`; `GET /billing/addons` returned no add-ons; `GET /custom-hostname` said it requires Pro. A grep of `*.md`, `scripts/` and `supabase/` for restore, backup, pg_dump and pitr found no restore guidance. Read-only SQL showed the three `_backup_20260918_*` tables live, referenced only by `src/lib/supabase/types.ts`. The Free-plan pause and retention terms are Supabase's published policy, not verified through the API. Verifiers: 3/3 upheld, all three lowering it from High to Medium because every loss path needs an operator mistake or a commissioner's deliberate action, not an ordinary user or attacker.

**OPS-5 · A failed profiles read silently turns Spoiler-Free off and shows unwatched results** — Medium
- **Where:** [account-settings-data.ts:48](../src/lib/account-settings-data.ts#L48) (destructure at `:29`); [score-history-data.ts:50](../src/lib/score-history-data.ts#L50) (read at `:35`); [spoiler-cutoff.ts:57](../src/lib/spoiler-cutoff.ts#L57).
- **What's wrong:**
  - `getAccountSettingsData` ignores the `profiles` read error and returns `spoilerFreeMode: data?.spoiler_free_mode ?? false`.
  - That value feeds `resolveSpoilerCutoff` on Home, Results, Picks and Standings (through `loadLeaguePageBase`), Manage Leagues, the league switcher (`loadHomeLeagueData`), waivers and admin Scores. With the mode false, the cutoff allows every completed week and ignores `last_watched_week` (`spoiler-cutoff.ts:57-65`). Score History does the same.
  - It's the only part of the gate that fails open: `loadSpoilerProgress` ([viewer-season-data.ts:21](../src/lib/viewer-season-data.ts#L21)) also ignores errors but falls back to week 0, which is closed.
  - The failure also hides the Spoiler-Free strip and live-air chrome (`buildLiveAirChrome` gets false), so nothing on the page signals the mode is off.
- **Why it matters:** on a live night a Spoiler-Free West Coast viewer who is behind keeps Home or Results open, and `RevealAutoRefresh` re-renders it every 20s. One failed profiles query in any of those renders (a PostgREST timeout or 5xx, a network blip from Vercel) shows every completed week, including the elimination just published. Each night gives hundreds of chances, and a spoiler can't be unseen. At current load a single failure is rare, but the gate fails open. Only completed weeks leak; revealing and draft weeks stay gated by `scoredWeekIds`.
- **Fix:** check `error` on the profiles read in `account-settings-data.ts` and `score-history-data.ts` and throw (or return an error in the Score History case), so `error.tsx` shows Try Again and nothing renders. Prefer throwing to defaulting to `true`: a `true` fallback would hide results from viewers who aren't Spoiler-Free and show them a strip they never turned on. Throwing also fixes Settings showing the toggle as off when the read fails. In general, any read that feeds a gate should fail closed.
- **Evidence:** code read as above; `accountSettingsData.spoilerFreeMode` feeds cutoffs at `(fan)/page.tsx:56`, `this-week/page.tsx:95`, `league-page-data.ts:121`, `leagues/(manage)/page.tsx:40`, `admin/results/page.tsx:55`, `leagues/[id]/waivers/page.tsx:144` and `leagues/[id]/switcher/actions.ts:30`. The scratch vitest `operations/spoiler-failopen.test.ts` (fake client: profiles returns `{data: null, error: PGRST003}`, `spoiler_watch_progress` returns `last_watched_week` 1) passed: `spoilerFreeMode` came back false and `visibleEpisodes` was weeks [3, 2, 1] instead of [1]. Verifiers: 3/3 upheld, lowering it from High to Medium because the trigger is a transient infrastructure failure, not something a user can cause.

**OPS-6 · Google sign-in from an invite link copied in the iOS app fails, because the app's host only allow-lists a bare callback** — Medium
- **Where:** [actions.ts:58](../src/app/auth/actions.ts#L58); [copy-invite-link-button.tsx:21](../src/components/copy-invite-link-button.tsx#L21); [capacitor.config.ts:8](../capacitor.config.ts#L8); [join page.tsx:80](<../src/app/join/[code]/page.tsx#L80>); co-manager invites at [co-manager page.tsx:67](<../src/app/join/co-manager/[code]/page.tsx#L67>).
- **What's wrong:**
  - `signInWithGoogle` builds `${origin}/auth/callback?next=/join/CODE`.
  - The allow-list has only the exact `https://dwts-fantasy-mirrorball-madness.vercel.app/auth/callback` for that host, with no `/**`, so any callback carrying `?next=` is rejected. GoTrue then falls back to `site_url`, which is the other host (`https://mirrorball-madness-kylie8.vercel.app/`). Both hosts serve the same deployment.
  - Invite links are built from `window.location.origin`, and the iOS app's `server.url` is the `dwts-fantasy-mirrorball-madness` host, so a commissioner copying an invite in the app hands out links on that host.
  - Google sign-in inside the iOS app itself is unaffected: it uses the native path ([google-sign-in-button.tsx:31](../src/components/google-sign-in-button.tsx#L31)) and the allow-listed custom scheme. Only app-copied links opened in a browser, and any browser Google sign-in on that host that carries `?next`, hit this.
- **Why it matters:** an invitee opens the link, taps Sign In or Sign Up, then Continue with Google. Afterwards they land on the other host's root holding a `?code` that host has no PKCE verifier for (the cookie is on the first host). A full script CSP can come later. The iOS wrapper loads the app as a top-level WebView, so `frame-ancestors 'none'` shouldn't affect it; confirm on a device.
- **Evidence:** `curl -D -` of `https://dwts-fantasy-mirrorball-madness.vercel.app/` showed only `strict-transport-security` among security headers; `next.config.mjs` at HEAD. Verifiers: 1/1 upheld; reworded the "why" around SameSite.

**OPS-19 · The live-reveal and retroactive recompute read `roster_slots` and `grand_finale_predictions` across every league and season, so rows past PostgREST's 1,000-row cap are silently dropped** — Low
- **Where:** [results.ts:279](../src/lib/results.ts#L279) (also `:277-282`); [recompute-published-weeks.ts:90](../scripts/recompute-published-weeks.ts#L90).
- **What's wrong:**
  - `recomputeWeekScores` reads `roster_slots` (279), `grand_finale_late_unlocks` (281) and `grand_finale_predictions` (282) with no league, season or week filter, no `.range()` and no `ORDER BY`. It also reads `leagues` and `scoring_settings` (277-278), but those only matter past about 1,000 leagues, and a truncated `leagues` list just skips the missing leagues rather than writing wrong rows.
  - With `max_rows` 1000, anything past row 1,000 is dropped with no error. `buildWeeklyScoreRows` pays nothing for a missing roster slot or bracket row, and the loop at 292-299 deletes and re-inserts that week's `weekly_manager_scores` for every league.
  - Publish is unaffected, since `episode_publication_snapshot` is a single jsonb value. Reveal mode passes `[]` as the episode's outcomes (`results.ts:243-250`), so Grand Finale never runs there. - **Why it matters:** `grand_finale_predictions` already holds 368 rows after one season (96 per Grand Finale league: 6 brackets × 16 couples) and is never pruned by season. It passes 1,000 at about 10–11 such leagues, or within two more seasons at today's size. After that, a retroactive recompute would silently rewrite published weeks with some managers' Grand Finale points missing. `roster_slots` (50 now, also never season-scoped) passing 1,000 would make each per-couple Publish write standings missing some managers' judges points until the official publish overwrites them. This is the same truncation class as OPS-10, but here it writes standings instead of affecting display.
- **Fix:** scope the reads to what the week needs: `.in("league_id", leagueIds)` plus the active season's couple ids for `roster_slots` and `grand_finale_predictions`, and `.eq("week_id")` (already done for `predictions`). Or build the inputs from `episode_publication_snapshot` the way publish does, so reveal, publish and the script share one non-truncating read.
- **Evidence:** read `results.ts:217-301` and `weekly-score-rows.ts:73-75` and `:117-180`. Read-only SQL: `roster_slots` 50, `grand_finale_predictions` 368 (96 per league for the top 3), `grand_finale_late_unlocks` 3, `predictions` 93, leagues 5. Management API `GET /postgrest`: `max_rows` 1000. Verifiers: 1/1 upheld.

**OPS-20 · The publish snapshot covers every prediction in every league and week, so a fan saving next week's pick during a publish makes it fail** — Low
- **Where:** [schema.sql:3561](../supabase/schema.sql#L3561) (snapshot); lock and compare at `:3591-3610`; [episode-publication.ts:176](../src/lib/episode-publication.ts#L176); caller `src/app/admin/results/actions.ts:139`.
- **What's wrong:** `episode_publication_snapshot` aggregates every row of `predictions`, `grand_finale_predictions`, `grand_finale_late_unlocks`, `roster_slots`, `scoring_settings` and the full `leagues` rows (3561-3566), with no season or week scope. `commit_episode_publication` takes its locks only after TypeScript has computed the plan, rebuilds the snapshot and raises "Results or scoring inputs changed. Refresh and try again." if anything differs. So any unrelated write between the snapshot read and the commit (`episode-publication.ts:171-192`) fails the publish: a Week N+1 Curtain Call pick, a league rename or settings change, another league's draft clock tick on `leagues.current_turn_started_at`, a waiver claim.
- **Why it matters:** results are usually published right after the show, which is exactly when managers start next week's picks. Each collision returns an error to the super admin and the publish has to be retried. The window is well under a second, so even with many managers it's occasional and costs one retry. The snapshot (and the `p_snapshot` sent back over PostgREST) also grows with every prediction ever made, across all seasons, and is rebuilt while 24 tables are held in `SHARE ROW EXCLUSIVE`.
- **Fix:** the smaller fix: retry once automatically on that exact error in `publishEpisodeAtomically`. It can't change scoring. Narrowing the snapshot to what the publish reads (this week's predictions and late unlocks, the active season's Grand Finale predictions and roster slots, only the scoring columns of `leagues`) also shrinks the payload and lock time, but must keep every input `buildPublicationPlan` and `buildWeeklyScoreRows` read, including Grand Finale predictions and late unlocks across all leagues for the season.
- **Evidence:** read `schema.sql:3550-3575` and `:3576-3610`, and `episode-publication.ts:171-192` (snapshot RPC, then TS plan, then commit RPC, no retry). CLAUDE.md documents the refresh/retry behavior; what's new is that unrelated fan writes trigger it. Verifiers: 1/1 upheld.
