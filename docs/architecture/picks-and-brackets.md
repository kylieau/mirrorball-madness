# Curtain Call and Grand Finale

The weekly picks (Curtain Call) and the season bracket (Grand Finale): locks, the Finale, positions, late entry and admin backfill.

Dated notes such as "(Kylie, 2026-11-10)" record when that behaviour was settled.

- **Curtain Call lock** is computed, never stored: `prediction_lock_at(league, week)` = the week's first night on the league's coast (`leagues.prediction_lock_coast`: `east` = `episodes.airs_at`, `west` = 8pm PT that day, the West feed) minus `prediction_lock_hours_before_air` (negative = after the curtain), capped at the end of that broadcast (`duration_minutes`) so picks never stay open past the elimination (`supabase/apply-west-coast-pick-lock.sql`). Submits, peer-pick visibility (RLS), Home, Picks and copy-picks all read that one RPC; `curtainCallLockAt` (`src/lib/curtain-call-lock.ts`) mirrors it only for the League Settings "Week N locks …" preview. Set in League Settings → Curtain Call (Air Time + Pick 'Em Lock hours Before/After the Curtain). The Grand Finale deadline stays on East time. The audit deadline migration preserves an established expired deadline through anchor/schedule/draft-reset edits; A commissioner can change Curtain Call timing at any time, even to reopen a week that has already locked or lock an open one immediately (`supabase/apply-drop-curtain-call-lock-guard.sql` removed the server guard); League Settings asks them to confirm either flip first (`pickLockFlip`). Genuine season rollover and intentional scoring exemptions remain supported.

- **Curtain Call admin backfill**: a site admin records a pick a manager made in time but couldn't save (a text before the lock) from League Settings → Curtain Call → Record a Pick (`CurtainCallBackfill`, any league, including ones they aren't in). It calls `admin_backfill_prediction` (`supabase/apply-curtain-call-backfill.sql`), which refuses anyone but a site admin, requires a reason and a pick time in the past and before that league's lock for the week (`prediction_lock_at`), and stamps `predictions.entered_by` / `entered_via = 'admin_backfill'` / `entry_reason` / `pick_made_at`. The form shows the manager's current pick first, since saving overwrites it. A backfill for an already published week only changes points when that week is next published. App submits still leave those columns null until the audit-remediation provenance migration replaces `submit_prediction`. There is no Curtain Call late-unlock window; this is the only way in after the lock.

- **Curtain Call's Finale podium (Kylie, 2026-11-11, `docs/design/curtain-call-finale-podium/`; `supabase/apply-curtain-call-podium.sql`, rehearsed in `curtain-call-podium-db.test.ts`, applied live 2026-11-11 and verified, types regenerated, and run once more that day for the check that every picked couple is in the week's season; safe to run again):** nobody goes home in the week marked Finale, so that week's elimination pick is three picks, Winner, Runner-Up and Third Place; top scorer is unchanged. Each place pays that week's elimination payout (`curtainCallPayout`; 3.23 at the defaults with five finalists), half of it one place off and nothing two off (`PODIUM_PLACE_OFF_FRACTION = 0.5`, `podiumPickPoints`), always on, whatever the In Jeopardy toggle; 4th and 5th are entered as Eliminated and count as 4th unless Finish Week gives one 5th Place (`podiumPlaceByCouple`, reading the result's `final_place`). Stored as three nullable columns on `predictions` (`predicted_winner_couple_id`, `predicted_runner_up_couple_id`, `predicted_third_place_couple_id`), written by `submit_podium_prediction` (Finale week only, all three places or none, three different couples; `submit_prediction` refuses an elimination pick for the Finale) and, for a site admin's backfill, `admin_backfill_podium_prediction`. Every reader goes through `src/lib/curtain-call-picks.ts` (`CurtainCallPick` with `podium`, `CURTAIN_CALL_PICK_COLUMNS`, `curtainCallPickFromRow`, `curtainCallPickMade`), so a `predictions` select never lists the pick columns by hand: the engine (`predictedPodiumCoupleIds`, `resolvePodiumGuess`), Score History (`Winner: Harry ✓`, `Third: Maura · Off 1 place`), the Picks card (`PickEmBox`, hint from `podiumPreviewCopy`), the recap (`PodiumRows`), League at a Glance, copy-picks, Results' gold lines (`podium winner pick`, so it doesn't read as Grand Finale's winner pick), the Home card (`Win:` / `2nd:` / `3rd:` rows, "Need podium & High picks") and League Settings' rule note (`podiumRuleNote`). Because those selects name the new columns, the app must not be deployed before the SQL.

- **Cross-league picks** (Curtain Call + Grand Finale) are a one-time copy via `submitPredictionToLeagues`/`submitGrandFinalePredictionToLeagues`, never a link — the RPCs stay the authority on membership/module-off/lock; `planDestination` (`src/lib/copy-picks.ts`) only decides what to offer.

- **Grand Finale** ranks the whole season cast (eliminated couples included). Couples whose elimination is already revealed to the viewer are pinned first via `pinEliminatedFirst` (`src/lib/grand-finale-pins.ts`); pinning is UI-only, the RPC doesn't enforce it.

- **The finale only has about 4–5 couples**, and they are not eliminated one by one: they receive final placements (1st–5th; only winner/runner-up/third are stored as statuses; 4th/5th are derived from elimination order, and couples out in the same week each take the best placement in their shared range, `finalPlacementFromRange`, matching Grand Finale's best-of-range. **In the week marked Finale only** (Kylie, 2026-11-24, `supabase/apply-finale-places.sql`), Finish Week's status list adds **4th Place** and **5th Place**: the couple stays `eliminated` everywhere (survival, Lifeline, Recast, spoilers, every status check), and the place is stored as `final_place` (4 or 5) on `draft_episode_results` / `episode_results` (dropped by the SQL on anyone not Eliminated or outside the Finale) and on `couples`, set by the publication plan's `coupleUpdates`. `eliminationPositionRanges` gives such a couple its own position (only while its status reads Eliminated, so a spoiler-clamped couple hides it), so Grand Finale scores it exactly and Dance Card v1 placement follows; blank keeps the shared 4th. Score History, the Picks recap and the shared couples loader read it; fan labels still say Eliminated). So a 16-couple season has roughly 11–12 real eliminations across the regular weeks, which is why some weeks must be flagged `is_double_elimination_week`. Never assume one elimination per week or that every couple is eliminated; **Doubles are never known ahead of time**, only once the episode airs, so `is_double_elimination_week` is the default plan, not truth. `slotWeeks` (`src/lib/scoring.ts`) maps a Grand Finale spot to a week using the real elimination counts for weeks that have happened (through the scored week, or the viewer's cutoff on Picks) and one per later week, and treats every spot after the last regular week as the Finale (`seasonFinaleWeek`: the week marked Finale, else the last).

- **Grand Finale positions**: 1 = first eliminated .. N = winner. `eliminationPositionRanges` (`src/lib/scoring.ts`) gives couples eliminated the same week a shared range (a double elimination is 2 wide; a no-elimination week takes none), and both the scoring engine (`results.ts`) and the Picks UI use it. `grandFinalePredictionPoints` credits a prediction inside its couple's range as exact; `grandFinaleBestCasePoints` is the "up to N" ceiling for a couple still in (it can only finish at or after the next open slot). **Distance scoring counts weeks, not spots** (Kylie, 2026-11-10, `grandFinaleDistance`): how many weeks lie between the week a spot falls in and the week the couple went home, so a double is one week and a week without an elimination still counts; the Finale is one week too, split evenly between its places (Kylie, 2026-11-11; `SlotWeeks.finaleSpots`, the couples left after the weeks before it): with five finalists a place off costs a fifth of a week, so a couple that reached the Finale always pays more than one that went home the week before. The change touches no week before the Finale. Exact-position and band scoring are unchanged. Score History says `Off 2 wks` / `Off 1 place`; League Settings' field is Points Lost per Week Off. Weeks 1–9 of S35 were recomputed for it on 2026-11-11 with `scripts/recompute-published-weeks.ts` (33 of 200 rows, only Grand Finale points moved; the replaced rows are in `weekly_manager_scores_archive`; `--verify` matched). **The week count is fixed by the Finale tick on Schedule** (`competition_weeks.is_finale`, Week 11 in S35): every scoring path reads it through `seasonFinaleWeek`, pinned in `weekly-score-rows.test.ts`. With no week marked it falls back to the last scheduled week, and marking or moving the Finale after weeks are published only reaches those weeks when each is republished or that script runs. Changing position logic only affects points on the next publish/correct of each week. A couple eliminated before the league's Anchor Week (`judges_score_starts_week`) was never a scoring opportunity: the engine pays nothing for it and the Picks row shows "—" (`PointsTag`, via `GrandFinaleScoring.scoringStartsWeek`).

- **Grand Finale late entry**: after the deadline, a commissioner (or a super admin, in any league, including one they aren't in) unlocks one manager for another manager from League Settings → Grand Finale (open that module's accordion) → Missed the lock, via `unlock_grand_finale_late` (`supabase/apply-grand-finale-late-unlock.sql`). The sheet is a percent of Grand Finale (slider and type-in, default 100%), stored as `late_factor` = percent/100. The manager gets one submit through the existing Grand Finale card (`Late entry · N% of Grand Finale`), then `submit_grand_finale_prediction` re-locks. Couples already resolved at that submit are snapshotted on the unlock row and never pay, including on a republish — the confirm sheet warns and requires an opt-in, and does not hard-block. Points are raw Grand Finale × `bonus_picks_category_weight` × `late_factor`. Score History and League at a Glance add `× N late` only when the percent is below 100. The unlock does not bypass Spoiler-Free. Before the manager submits, the commissioner/super-admin can **edit the percent** (Edit % — `unlock_grand_finale_late` upserts the still-open row rather than raising) or **close it outright** (Close — `close_grand_finale_late`, `supabase/apply-grand-finale-late-edit-close.sql`); both refuse once the manager has actually submitted. Editing an already-locked bracket, self-unlock, and retro-pay are out.
