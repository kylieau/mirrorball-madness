# Results Entry and Publishing

How a night's scores get from Enter Results to every league: drafts, per-dance posting, Finish Week, rounds and special dances. Admin pages are `/admin/results` (Scores) and `/admin/results/enter` (Enter Results).

Dated notes such as "(Kylie, 2026-11-10)" record when that behaviour was settled.

- **Scores and Enter Results are separate pages**: `/admin/results` (titled "Scores", By Week / By Couple via `?tab=`) and `/admin/results/enter` (Enter Results; `?episode=` opens a week directly, which is how Scores' "Continue in Enter Results" links there). `/admin/results?tab=enter` redirects to the new page, and a viewer without propose access who opens `/admin/results/enter` is sent back to Scores. Results actions revalidate `/admin/results` with `"layout"` so both refresh. Scores' dance lines name a special dance's row by its name (`Dance-Off 1 · Rumba: +2`, a points row signed), and an immunity bonus without a style (`Dance-Off Immunity: +2`), from `specialDanceLabels` built off `teamsByEpisode`.

- **Results entry has three access tiers** across those pages (Scores is "View"): **View** (any signed-in user — seeing how results get entered is deliberately open), **Propose** (`is_super_admin` or explicitly approved `profiles.can_propose_results`, via `requireProposeAccess()` — writes only to `draft_*` tables, zero live effect until publish), **Admin/Publish** (`is_super_admin` only, via `requireAdminAccess()` — publishing recomputes every league's scores). Client-side hiding of actions per tier is UX only; the action-level checks are the real enforcement.

- **Admin Schedule access**: same two tiers as Results minus Propose — any signed-in user can view `/admin/schedule`, only `is_super_admin` can edit (`readOnly` prop, `ScheduleManager`); the writes it calls, `scheduleEpisode` and `updateSeasonSettings` (both in `src/app/admin/results/actions.ts` — Schedule has no `actions.ts` of its own), are gated server-side by the same `requireAdminAccess()` Results uses, not by the client's `readOnly` flag. **Season Settings lock**: the Premiere/Total Episodes/Finale card greys out and locks once saved (a season with all three already set also opens locked, so it survives a reload), with an outline Edit button to reopen it for another pass — client-only state, no server-side "locked" concept. Episode/week-row locking is a separate, not-yet-built question.

- **Shared data loaders**: `/admin/results`, `/admin/results/enter`, `/admin/schedule`, and `/admin/show-settings` share season data (episodes, weeks, drafts, roster) via `loadResultsPageData` (`src/lib/results-page-data.ts`) so the query shape can't drift across pages.

- **Atomic draft lifecycle (prepared audit release):** draft saves, correction seeding and release/withdraw use service-only transactional RPCs with an explicit actor check. Published edits require a matching correction token and base publication timestamp; ordinary delayed autosaves cannot overwrite a published episode. Missing correction rows block publication. Settings writes use `update_scoring_categories_checked` with a revision; do not call the legacy RPC from the app. Invite secrets are excluded from table SELECT grants; only an owner RPC returns a live seven-day code.

- **Atomic results publication**: `publishEpisodeAtomically` (`src/lib/episode-publication.ts`) reads a consistent service-only `episode_publication_snapshot`, projects results/couple statuses, and computes every league's score rows through `buildWeeklyScoreRows` (`src/lib/weekly-score-rows.ts`, shared with reveal and retroactive recomputes). `commit_episode_publication` installs dances, judge scores, outcomes, couple statuses, future-cast pruning, weekly standings, custom moments, publication metadata and draft cleanup in one PostgreSQL transaction. It briefly locks the affected tables and compares the snapshot before writing; changed inputs return an error for refresh/retry, and any write failure rolls everything back. Both RPCs deny anon/authenticated execution; the action and SQL commit check super-admin access. `supabase/apply-atomic-episode-publication.sql` is applied live (RPC availability verified, types regenerated); a fresh project must apply it before deploying this code. Missing RPCs fail before any live write. No point rules changed. Autosave uses `DraftSaveQueue` edit revisions and serialized requests, drains newer edits before publish/release, and keeps failed edits dirty for retry.

- **Live score reveal (built):** on `/admin/results/enter` (Enter Results), the couples card lists, on each round's tab, every couple dancing it as a row (Kylie, 2026-11-24, `docs/design/enter-results-round-status/` B; the In progress / Drafted / Published chips and the couple dropdown are gone, since each dance posts on its own and a couple can be Published in one round and In progress in the next): the couple, that round's dance (`Cha Cha · Tears`), its total once marked and a status pill for that round's dance only (`coupleStatus`: **In progress**, **Ready to Publish** once every judge has marked it, **Drafted** after Save as Draft Score, **Published**; with no rounds, every dance of theirs). Tapping a row opens its entry in place, one at a time (`renderEntryRows`); with none chosen the first row still to publish opens, rows keep their order as statuses change, and a row tapped shut stays shut (`CLOSED_ENTRY`). A **Leaderboard →** gold text link at the top-right of the card title shows the score-sorted Leaderboard and reads **← Couples** while it does. A super admin publishes **one dance at a time** (Kylie, 2026-11-24): each of a couple's own dances has its own **Publish** once every judge has marked it (no confirm sheet; **Undo · Ns** for 30s, then **Un-Post**; `revealDanceScores` / `undoDanceScoresReveal` → `src/lib/results-reveal.ts` → `buildDanceRevealPlan` → `commit_dance_reveal`, by couple and round slot; `supabase/apply-per-dance-publish.sql`). `draft_dance_scores.live_dance_score_id` links a draft dance to the live row its post wrote, so un-posting removes only that dance; a posted dance is read-only and the couple's other rounds stay editable: `save_episode_draft_checked` accepts a posted couple's save while every posted slot arrives unchanged (else it skips the couple, as before) and saves the rest. The couple card shows Posted once any of its dances is, and Save as Draft Score is gone for it. The app before that SQL posts a whole couple through `commit_episode_reveal`, which now links what it writes; the file links couples already posted by matching each dance. The app must not be deployed before the SQL (the loader selects `live_dance_score_id`). Judges' Save Active is a Schedule setting (per episode), not a switch on Enter Results. Per-couple entry is only dances, songs and judge scores (a dance's judge boxes stay disabled until it has a style, since a draft save skips a styleless dance); a couple's dance rows default to the episode's `expected_dance_count` (fill-in-the-blanks, no "+ Dance" click per row; the plan's count of own rounds, see Episode rounds), except a Did Not Dance couple, which gets none. Each saved draft dance carries its round slot (`draft_dance_scores.dance_slot`, its round's place among the own rounds, 1 = the first, sent by `buildDraftInput` and placed by `placeDraftDances`, `src/lib/results-draft-input.ts`; `supabase/apply-draft-dance-slots.sql`), so a later round saved first reloads into its own slot; a row with no slot (older saves, copies of live dances) fills the first empty slot. A song typed with no style is not saved, and the slot says "Pick a dance style to save this dance." The week picker writes `?episode=` so a reload reopens that week. The app must not be deployed before that SQL, since the draft loader selects `dance_slot`. Removing or reordering own rounds renumbers the saved slots in `save_episode_rounds`'s transaction, refusing to drop a round with saved dances, to move rounds while a dance has no slot, or to remove or reorder a published week's own rounds; an Enter Results tab open across a plan change must reload before anyone types, or its next autosave writes the old slots back. The app must not be deployed before `apply-episode-rounds-reorder.sql` either: the old function moves rounds without moving their saved dances. Drafts autosave ~1.5s after each edit (`flushDraft`/`scheduleAutosave`); there is no manual Save Draft button, only the card header's live "Draft saved {X} ago" status line. **Saves are scoped to only the couples edited since the last save** (`dirtyCoupleIds` in `results-form.tsx`, sent as `entries` to `saveDraftResults`), not a whole-episode delete-and-reinsert — two trusted contributors entering different couples' scores at the same time can't silently wipe each other's rows the way an episode-wide snapshot save would. A couple edited by both at once still resolves last-write-wins; that narrower collision isn't guarded against. **Draft Scores / Withdraw Draft is per couple, propose tier** (any explicitly approved contributor, not just super admin — `requireProposeAccess` in `src/app/admin/results/actions.ts`), a deliberate exception to the usual admin-only release pattern so whoever's live at the ET broadcast can release one couple's dance at a time as it airs, instead of waiting on a site admin or on every couple in the night being scored; it's season-wide, not scoped to that contributor's own league. The control sits on each couple's own card (a "Save as Draft Score" button, or a "Drafted" badge + Withdraw once released), available to every propose-tier viewer whenever the episode is unpublished and that couple isn't already live-revealed — a couple can be draft-released or live-revealed, never both, and the two coexist independently within one night. Publish (per-couple or the correction-mode **Publish Results**) stays admin-only; the sticky bar only ever shows Publish Results, and only in correction mode (published + super admin). **Correcting a published episode is narrowed to one couple at a time**: selecting an already-published episode still transparently seeds a correction draft for the whole night (unchanged), but every couple's card now shows read-only by default with its own **Edit** button — clicking it is purely a client-side UI unlock (`unlockedForCorrectionCoupleIds`) that opens just that couple's fields, not a second draft or a different save path. Other couples stay read-only until their own Edit is clicked; re-publishing applies whatever's in the draft regardless of which couples were ever unlocked, since unrelated couples were already seeded to match what's live. Safe/eliminated, In Jeopardy, Judges' Save, Immunity and Bonus live in the **Finish Week** card as a checklist table (everyone defaults to Safe), which is disabled until every couple is posted and asks to confirm when a week that should have eliminations has none marked, and, from the East curtain until 10pm PT, first asks whether to wait for the West feed (`westFeedStillAiring`, `src/lib/episode-banner.ts`), since finishing shows who went home on every fan page (only Home's Recent Activity masks it); the sticky **Publish Results** remains only for correcting an already-published week. The old Score a Team Dance bulk-entry sheet is gone. There is no reveal table: a couple is "revealed" when it has live `dance_scores` rows while its episode has no `results_published_at` (`created_at` drives the 30s undo bar); reveal and undo use `commit_episode_reveal` to change dances and standings atomically. The plan changes judges points while preserving settled sibling-night predictions and bonuses; new outcomes wait for final publication. Autosave substitutes the live scores for a revealed couple so they can't drift, and Finish Week (and **Publish Results**) refuses until every couple with a drafted dance is posted and every dance of a posted couple is published (the SQL names it: `Publish every dance before finishing the week: Amber Glenn's Instant Dance is still to publish.`), then skips rewriting revealed dances (the atomic `commit_episode_publication` RPC preserves the live rows). Pure state (`unpostedCoupleIds`, `undoSecondsLeft`) is in `src/lib/reveal-state.ts`. Viewers read a revealing week through `loadRevealingWeek` (`src/lib/revealing-week-data.ts`) and `scoredWeekIds` (only once the viewer chose Stay Updated or Mark Watched for that week, whatever their Spoiler-Free setting): Home activity and league points, Standings points and rank arrows (which compare against the revealing week while there is one), Score History (judges lines only), the Couples Leaderboard and roster cards (judges points), and Results (`selectThisWeekEpisode` mode `scores`: posted dances, no outcomes). Outcome-dependent surfaces (Curtain Call recap, eliminations, Recast, `couples.status`) stay completed-only.

- **Draft scores before official publish:** an explicitly approved contributor or site admin (propose tier) releases one couple's drafted dance at a time with **Draft Scores** (`draft_couple_releases`, keyed `episode_id, couple_id`; `releaseDraftCouple`/`withdrawDraftCouple` in `src/lib/results-draft.ts`; server-gated by `requireProposeAccess`, not admin-only — season-wide, not scoped to the releasing commissioner's own league). Superseded the earlier whole-episode `episodes.scores_drafted_at` flag (dropped; required every couple scored before releasing anything, `supabase/apply-per-couple-draft-release.sql`). That does not write live `dance_scores` or `weekly_manager_scores`. `visible_draft_dance_scores()` joins `draft_couple_releases`, so only released couples' dances are ever readable; `draft_couple_releases` itself is readable by `authenticated` (no scores in it; `GRANT SELECT` plus a SELECT policy — RLS with no policy returns zero rows and hides the live-air prompt; `supabase/apply-draft-couple-releases-select.sql`), while the actual score rows stay behind that security-definer RPC. A couple already live-revealed (per-couple Publish, admin-only) drops out of the draft-release UI — the two mechanisms are mutually exclusive per couple, but independent per night: an episode's couples can be a mix of released, still-drafting and separately live-revealed, so every reader that merges live and draft dance rows for a week (`src/lib/draft-scores.ts`'s `excludeReleasedCoupleRows`/`replaceWeekDanceScores`, used by Home, Score History, Standings and the Couples Leaderboard) excludes and merges **per couple**, never blanket-excludes a whole episode or week, and keeps a posted special dance's `team_id` row, since a draft holds only the couple's own dances. Draft-night league standings and Home league cards score `draftNightDanceScores`: the released drafts plus every live row of that week's nights (`liveDances`, loaded by `loadDraftScoreContext` only once the viewer can see the draft). `set_draft_couple_release` likewise counts only own rows (`team_id is null`) as "already live" (`supabase/apply-draft-release-own-rows.sql`, applied live 2026-11-04). A viewer who chooses **Mark Watched** (Live Scores Prompt, the Spoiler-Free strip, Results/Picks catch-up, or moving "I last watched" forward — `unlock_draft_scores_through`) can see released dances and judges-only standings. **Stay Updated — I'm Watching Live** on the live-air prompt unlocks drafts too during the East window, but only advances `last_watched_week` (published scores, no drafts) during the West window. The Draft scores available pill does the same during the West window; in the gap and during East it still unlocks drafts. After West Stay the Spoiler-Free strip is Watching live · Week N, and the amber strip stays hidden. While drafts are visible, Home, Results, Picks and Standings each show one amber soft-inset strip (`Draft scores · Unverified`, info sheet, Pattern B: pinned page title + strip) and hides the Spoiler-Free strip. Official publish (still admin-only) clears every release for that episode (`deleteAllDraftRows`). **A special dance releases the same way** (propose tier, Save as Draft Score / Drafted · Withdraw on its card, `setSpecialDraftReleaseAction` → `set_special_draft_release`, `supabase/apply-special-draft-release.sql`, applied live 2026-11-04): `draft_special_releases` (one row per dance, readable by `authenticated`) marks it, and `visible_draft_special_scores()` returns one row per eligible participant shaped exactly as posting writes it (marks over the panel's possible, or points with `max_score = 0`, never the Result text), only while the dance is fully scored, unposted and its episode unpublished. A released special has no live rows, so its members never join `releasedCoupleIdsByEpisode` (`releasedTeamIdsByEpisode` instead); `findDraftRelease` counts either. Every reader turns `night.dances` into scoring rows through `draftDanceScores`, which keeps `maxScore` / `teamId`, and `replaceWeekDanceScores` lets only a couple's own drafted dances stand in for its live own rows. Publish, Finish Week and un-post leave release rows alone; reads hide a posted dance's or published night's release, and un-posting brings it back, as for a couple. Home curtain status is unchanged.

- **Announced lineup:** a couple's style and song autosave on Enter Results with no scores, and signed-in fans see them before publish: on Results' "Results aren't in yet" card for that week (peek mode only, so a Stay Updated viewer loses it once scores post) and under each couple in Picks' Curtain Call dropdowns while picks are open (the closed trigger still reads the name from `items`). `visible_draft_lineup()` (`supabase/apply-draft-lineup.sql`, applied live 2026-11-05, `draft-lineup-db.test.ts`) returns style and song for the active season's unpublished weeks only, never a score, never a published week's correction seed, and not to `anon`. `weekLineup` (`src/lib/draft-lineup.ts`) keeps it empty until the viewer has watched every earlier completed week, since who is still dancing gives away who went home. A missing RPC reads as no lineup. Couples' own dances only; special dances are not listed.

- **Episode rounds (Edit Episode → Dance Rounds For This Episode; `supabase/apply-episode-rounds.sql`, rehearsed in `episode-rounds-db.test.ts`, applied live 2026-11-05 and verified with `supabase/queries/verify-episode-rounds.sql`):** an episode's night is a list of `episode_rounds` (a new episode starts with the couples' own Individual Dance, which can be renamed, moved with ↑ ↓ or removed like any round, Kylie 2026-11-24, `supabase/apply-episode-rounds-reorder.sql`; a plan keeps at least one `own` round; kinds `own` = one more dance per couple, `special` = heats or teams, `none` = elimination only, never scored). It replaced the Dances (Per Couple) count and the Round Types ticks: `save_episode_rounds` (site admin, one transaction, from the Schedule sheet's Save) writes the rounds, creates, re-pairs, renumbers or drops a special round's heats (`episode_teams.round_id` / `heat_number`; a heat with scores or posted refuses to go), applies exceptions, and sets `expected_dance_count` (own rounds) and `episode_round_types` from it. Special rounds are scored `fixed_bonus` (Winner's Bonus: heats in points, a Winner takes `episode_rounds.bonus_points`, a Loser 0), `couple_marks` (Judges' Marks per couple: `episode_team_couple_marks`, a heat's special dance in `scoring_mode = 'couple_marks'`, each member paid their own marks over judges × 10; `PLAN_VERSION = 3`), `ranked_points` (points typed by finish) or `team_marks` (today's shared marks). Exceptions (`episode_round_exceptions`, service-only: notes) are Immune, Not Dancing or Withdrawn per round; Withdrawn always spans the night. `save_round_exception` (propose tier, Enter Results' Mark an Exception and Not in This Round band) takes the couple out of that round's heats (an emptied heat goes back to a placeholder; a posted one refuses), sets the draft outcome (Withdrawn, or Did Not Dance when every round is Not Dancing, back to Safe when that stops being true) and ticks Immunity; an immune couple's bonus is the round's immunity row (`heat_number` null, a one-couple Points dance) at their own bonus or the round's winner's bonus (`sync_round_immunity`), blank until the bonus is known (which holds Finish Week). `set_round_bonus` (propose tier) sets the bonus on air and refills Winner rows and the immunity row. An immune couple's own bonus stays editable on their Not in This Round row (`ImmuneBonusField`, saved through `save_round_exception`, which updates it in place); blank follows the winner's bonus. A heat in a Winner's Bonus round is entered by picking its winner (Kylie, 2026-11-10): one button per couple (`Tap the Winner`), the pick saves Winner at the round's bonus and everyone else Loser at 0, and only Clear empties it (a second tap does nothing); the picks wait while a Winner's Bonus save and its refresh are in flight, so an old bonus can't overwrite the server's refill. A heat saved another way (a Tie, two Winners, points that don't match) keeps the points boxes and Result dropdowns, as does every other points dance. The immunity row isn't a dance (Kylie, 2026-11-10): its card has no Edit Details and no style line (it reads "Immune this round, so no dance: a bonus only."), and a couple marked Immune, Not Dancing or Withdrawn in a round can't be a participant in that round's heats: Enter Results leaves them out of the list (`outOfRoundCoupleIds`) and `supabase/apply-immune-heat-guard.sql` (a deferred constraint trigger on `episode_team_members`, checked at commit on the final rows so a plan save that clears a mark and re-pairs the couple in one go still works; rehearsed in `episode-rounds-db.test.ts`; the immunity row is exempt) refuses it. Enter Results shows a Rounds switch once there is more than Round 1: an own round shows each couple's matching dance slot; a special round lists its heats (placeholders open a pre-filled new entry, named by `round_heat_name`, "Dance-Off 2") plus the immunity row; an elimination round shows a note. Pure logic: `src/lib/episode-rounds.ts`; reads: `loadEpisodeRounds` (`src/lib/episode-rounds-data.ts`, exceptions through the service client). The backfill gave every episode a plan (E09: Round 1 + Team Dance, 2 teams; E10: Round 1 + Dance-Off, 3 heats by Winner's Bonus, "Dance-Off" renamed "Dance-Off 1", a hand-made Immunity special folded in as its immunity row). The previous app build still works against this SQL unless a couple-by-couple heat exists.

- **Special Dances (Enter Results, admin UI only):** a special dance is its own entity (team dance, trio, dance-off, marathon, …), never a couple. Rows still live on `episode_teams` (no table rename); they reach scoring only as `dance_scores` rows tagged `team_id`. Setup is inline on Enter Results (`SpecialDanceEntry`, `src/components/special-dance-entry.tsx`): Dance Type, Participants, Style (+ second), Song (up to 4, its source in parentheses like couples' songs, `Zoo (Zootopia 2)`), Scoring (Judges' Marks or Points per Couple), collapsed More Details (Team Name), Extra Details (suggested Captain, Host, Live Performer, Mentor). There is no Artist or Theme / Source field (Kylie, 2026-11-04: fans never saw them and couples' songs carry neither); the app no longer reads or writes `songs[].artist`, `song_source` or `theme_label`, and `supabase/apply-retire-special-leftovers.sql` drops them (rehearsed in `retire-special-leftovers-db.test.ts`, applied live 2026-11-05 and verified). A points dance's Result suggests Winner, Loser, Immune. **Setup and Remove are propose tier on an unpublished week** (`requireProposeAccess`; `save_special_dance` / `delete_special_dance` via `supabase/apply-contributor-special-setup.sql`, applied live 2026-11-04), so whoever is entering scores can create a dance-off as it airs; a published week and an already posted dance (whose style and song rewrite its live rows) stay admin only, checked under the episode lock. There is no Edit Teams sheet, no header Set Up / Edit Teams, and no Teams section on Schedule. Special dances outside the round plan are rows under the couples on Round 1's tab (or with no rounds), A–Z by short name, with the Dance Type and Oxford-comma first names under it and Published or Drafted as their status; a special round's own tab lists its heats and immunity row the same way (a heat not set up yet reads "Not set up yet" and opens Set Up). Contributors and admins in special mode get an **Add Special Dance** button under the rows on an unpublished week. `coupleIdsForDraft` (`src/lib/results-draft-input.ts`) drops `team:` and `add-special` so a draft save never sends those as couple ids. **Judges' Marks** save as typed (`save_team_marks`, propose tier) from the night's judges (standing panel plus guests, 2–4), out of 10; there is no per-dance panel or "Out of": every special dance is out of 10 on the night's judges (`special_dance_panel`); `supabase/apply-retire-special-leftovers.sql` drops the old `mark_max` / `panel_judge_ids` columns; **Points per Couple** save through `save_special_dance_points` (propose). **Judge marks are whole numbers from 1 to 10 for couples and special dances alike** (`isValidMark` / `JUDGE_MARK_MESSAGE`, `src/lib/judge-marks.ts`; the `*_whole_mark` checks on `judge_scores`, `draft_judge_scores` and `episode_team_marks` in that SQL file, applied live 2026-11-04). Both enter through one `JudgeScoreRow` (`src/components/judge-score-row.tsx`: every judge's box and the total out of judges × 10 on one line, the names shrinking together to fit their columns on one line, no guest marker, an invalid box outlined with the rule stated once under the row). A couple holding an invalid mark is left out of the draft save by name while the other couples save. The dance's own **Publish / Undo · Ns / Un-Post / Re-post** stays admin (`commit_team_reveal`). Posting writes one live `dance_scores` row per eligible member tagged `team_id` (`materialize_team_scores` / `team_eligible_members()` / `eligibleTeamMembers`): marks rows store `total_score`/`max_score` and `scaled_score` on that scale; points rows store the points with `max_score = 0` and no `judge_scores`. Every reader still sums a couple's rows in an episode: Dance Card collapses own + special through `collapseToNights` (28/40 + 36/40 = 64/80 → 24; a +3 dance-off is 67/80 → 25.13, above 30 when the night is already full marks). A couple's draft never holds special-dance rows: **a couple posts its own dances independently** (`commit_episode_reveal` looks only at `team_id is null` rows), and the special dance posts on its own; each step recomputes the week's judges points (`buildTeamRevealPlan`, `src/lib/episode-reveal.ts`). **Finish Week** (`commit_episode_publication`) installs the couples' own drafts, keeps a posted couple's own rows (which must agree with their draft, `episode_couple_dance_signature`, own rows only), then materializes every special dance (`special_dance_complete` / `special_dance_blocker` instead of a hard-coded four marks) and **refuses by name** while a dance with members is incomplete; `buildPublicationPlan` mirrors all of it (`teamScoreRows`, `PLAN_VERSION = 2`). A plan without `planVersion: 2` is refused only when the episode has a Points dance (`assert_special_dance_plan`); pre-migration snapshots still use `LEGACY_TEAM_PANEL_SIZE = 4` so new code without the SQL behaves as `71328d3`. A couple whose only live row is a special dance's is **not** "posted". `seed_episode_correction` copies only own rows; a published special dance is corrected through its marks or points and re-materialized on Publish Results. A posted dance cannot have its participants or scoring mode changed. Member cards list every special dance as a read-only line with `Open →` plus the combined night; the Leaderboard adds a **Night Summary** (`buildNightSummary` with `parts` / `label`). **Naming** (Kylie, 2026-11-06, `docs/design/special-dance-names/`): one rule in `src/lib/special-dance-names.ts` — the short name is the dance's own name (`Slaytopia`, `Dance-Off 2`, `Dance-Off Immunity`; fans see heat numbers too), the full name puts the Dance Type in front unless the name already says it (`Team Dance · Slaytopia`, `Dance-Off 2`). Fan Results lines and couple history use the short name (`Slaytopia · Zoo`, `coupleDanceLines` / `nightDanceLabel`) and list a night's dances own first, special dances under them, a bonus-only row last, whatever order they were posted in (Kylie, 2026-11-11, `orderNightDances`, `src/lib/night-dance-lines.ts`: Results cards and their score parts, All Results, couple history; Home's Recent Activity stays newest post first and the Night Summary keeps its own order), Home reads `earned +3 in Dance-Off 1` / `with Dance-Off Immunity`, member cards the full name, the Night Summary short names with bonuses signed (`Individual 26 + Dance-Off 1 +3`). SQL error messages name a dance the same way through `special_dance_label` (`Team Dance · Slaytopia`; `supabase/apply-special-dance-label.sql`, rehearsed in `special-dance-label-db.test.ts`, applied live 2026-11-07 and verified), and Finish Week's TypeScript blockers call `specialDanceFullName`. Finish Week's bonus column is **Fantasy Bonus (pts)** and warns when that couple already has bonus-round points. **Feature detection:** `detectTeamsMode` (`src/lib/episode-teams.ts`) probes `episode_teams.scoring_mode` then `dance_scores.team_id`; `loadResultsPageData` reports `teamsMode: "special" | "entity" | "none"`. `supabase/apply-special-dances.sql` is live (probed 2026-11-03), so production runs `special`. The fallbacks remain for a fresh project: without it the app stays on the team-entity path (`SpecialDanceEntry` with `specialMode={false}`, marks-only, night panel must be 4); without `supabase/apply-team-dance-entity.sql` it never selects `team_id` and Enter Results has no special dances (the old inferred-teams fallback and `TeamEntry` are gone). **Typed marks and points live on the page, not the entry:** `SpecialDanceEntry` reports every edit (`onEditScores`, parsed payload or `invalid`) and `results-form.tsx` holds them in `specialEdits` and saves them through its own `DraftSaveQueue` (`specialSaveQueue`, 900ms debounce, one dance at a time with the edit's own episode id), so closing or reopening an entry, switching episodes or reverting a value never drops or reorders an edit.
