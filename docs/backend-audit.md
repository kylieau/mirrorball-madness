## Findings

**BE-1 · Any leaguemate can read every team's co-manager invite code and take over that team, including a commissioner's (up to `delete_league`)** — High
- **Where:** [schema.sql:1295](../supabase/schema.sql#L1295) (table-wide `grant select on public.league_members`); also the SELECT policy at [schema.sql:1369-1371](../supabase/schema.sql#L1369), `join_as_co_manager` at [schema.sql:1022-1067](../supabase/schema.sql#L1022), `is_league_commissioner` at [schema.sql:1349](../supabase/schema.sql#L1349), the realtime publication at [schema.sql:2397](../supabase/schema.sql#L2397), and the settings read at [settings/page.tsx:44](../src/app/leagues/%5Bid%5D/settings/page.tsx#L44).
- **What's wrong:**
  - The grant is table-wide, so it includes `co_manager_invite_code`. The only SELECT policy is `is_league_member(league_id)`, so any member can read every team's unredeemed code with their normal session: `supabase.from('league_members').select('co_manager_invite_code')`.
  - The League Settings page itself fetches every member's code; only [settings/page.tsx:120](../src/app/leagues/%5Bid%5D/settings/page.tsx#L120) hides the others, and that's client-side.
  - `league_members` is in the `supabase_realtime` publication and the draft room subscribes to it ([draft-room.tsx:227](../src/components/draft-room.tsx#L227)). When a code is minted, the UPDATE goes out to every member who passes RLS, and because of the table-wide grant the payload includes the code.
  - `join_as_co_manager` only checks that the code exists, the team has no co-manager, the caller isn't already in the league and no draft is running. It never checks who the code was issued to, and codes never expire.
  - `is_league_commissioner` counts `co_manager_id`, so a co-manager of a commissioner's team is a commissioner.
- **Why it matters:** Alice (commissioner) mints a code and texts it to her partner. Before the partner redeems it, leaguemate Bob reads it and redeems it with a second account (sign-up is open; a second account is needed because the join refuses anyone already in the league). That account can overwrite Alice's Curtain Call pick, Grand Finale bracket, draft queue and draft picks, rename the league, remove members, or call `delete_league`, which cascades every league row and can't be undone. Alice can detach the co-manager afterwards (`remove_co_manager`), but picks already changed stay changed, and the real partner's code is used up. Guessing a code blind isn't practical (6 characters from 31 symbols, about 887M combinations); the table read is what makes this exploitable.
- **Fix:**
  - Revoke the table-wide SELECT on `league_members` and grant SELECT on every column except `co_manager_invite_code`, following CLAUDE.md's column-level grant pattern. Realtime drops columns the role can't SELECT, so this also closes the realtime path.
  - No app query uses `select("*")` on `league_members`, so only the settings page's read breaks. Replace it with a security-definer `my_co_manager_invite_code(p_league_id)` that returns the code only for the caller's own primary row.
  - Add an expiry (e.g. `co_manager_invite_expires_at`) checked inside `join_as_co_manager`.
  - `get_co_manager_invite_info` ([schema.sql:1075-1090](../supabase/schema.sql#L1075)) also looks codes up by value. That's fine once codes can't be read by others, but check its grants when applying the fix.
- **Evidence:** PGlite with the full HEAD schema (`audit3/backend-gaps/comanager-hijack.mjs` / `.out`). As `authenticated` member B, the select returned V's code. Stranger C then ran `join_as_co_manager(code)`, which succeeded. `submit_prediction` as C stored `manager_id = V` with C's couple, overwriting V's pick; `is_league_commissioner` as C returned true; `rename_league` → "pwned", `remove_league_member(B)` and `delete_league` all succeeded (0 leagues left). Live, read-only: `has_column_privilege('authenticated','public.league_members','co_manager_invite_code','SELECT')` is true, the policy text is `is_league_member(league_id)`, and 1 unredeemed code exists right now (counted; the value was not read). The live `join_as_co_manager` hashes identical to HEAD. Verifiers: 3/3 upheld; the realtime leak path, the client-only masking at line 120 and the `get_co_manager_invite_info` note came from them.

**BE-2 · Spoiler-Free fails open when the profile read errors, so one bad auto-refresh can show eliminations** — Medium
- **Where:** [account-settings-data.ts:48](../src/lib/account-settings-data.ts#L48); also [account-settings-data.ts:29](../src/lib/account-settings-data.ts#L29), [spoiler-cutoff.ts:42-65](../src/lib/spoiler-cutoff.ts#L42), [score-history-data.ts:35](../src/lib/score-history-data.ts#L35) and [:50](../src/lib/score-history-data.ts#L50), [admin/results/page.tsx:54](../src/app/admin/results/page.tsx#L54), [results-page-data.ts:89](../src/lib/results-page-data.ts#L89), and the switcher's [switcher/actions.ts:23-30](../src/app/leagues/%5Bid%5D/switcher/actions.ts#L23).
- **What's wrong:** `getAccountSettingsData` reads `profiles` with `const [{ data }, memberships]` and ignores the error, so a failed read gives `spoilerFreeMode: data?.spoiler_free_mode ?? false`. With the flag false, `resolveSpoilerCutoff` allows every completed week. Home, Results, Picks, Standings, Recast, the switcher and Scores all take the flag from this loader. Score History repeats the pattern with its own `profiles` read. On Scores, the seasons read at `results-page-data.ts:89` also ignores its error while weeks and episodes are keyed off a separate `active_season_id` call, so a seasons-only failure gives `season = null` and `resolveSpoilerCutoff` allows everything. (On the fan pages a failed `active_season_id` read also empties the episode lists, so that path doesn't leak.)
- **Why it matters:** A West Coast Spoiler-Free viewer has Results or Home open during the West window, and `RevealAutoRefresh` re-renders every 20s. If one refresh's `profiles` request fails while the others succeed, that render treats the just-published week as watched: eliminations, outcome-dependent couple statuses and points. The fail-closed `spoiler_watch_progress` read doesn't help, because the mode flag short-circuits it. It takes a non-retried server error on that one request (postgrest-js retries GETs on network errors and 503/520, but not on a 504 pool timeout or a 500 statement timeout), so it's an infrastructure fault rather than something a user can trigger. Score History runs from a server action when a row is expanded, not on the 20s refresh, so it's exposed less often.
- **Fix:** Fail closed. Check `error` in `getAccountSettingsData` and `score-history-data`, and either throw (so `error.tsx` shows and the previous render isn't replaced with spoilers) or default `spoilerFreeMode` to true. On Scores, throw or fail closed when `data.season` is null but episodes exist. The switcher's `getSwitcherSummaries` uses the same loader and gets the fix for free.
- **Evidence:** Code at the lines above. Fake-client test with an erroring `profiles` select (`audit2/backend/backend-races.test.ts`, `races.test.ts`): `healthy read: allowed [ 'w3', 'w2', 'w1' ] | profile read error: spoilerFreeMode false allowed [ 'w5', 'w4', 'w3', 'w2', 'w1' ]`. A verifier reproduced it separately (`audit4/v1sf/sf.test.ts`). Verifiers: 3/3 upheld the bug, and all three lowered it from High to Medium because it needs a partial PostgREST failure with no user trigger; the retry detail and the `results-page-data.ts:89` path came from them.

**BE-3 · A draft left on a published episode (late autosave, partial seed) republishes as the whole night** — Medium
- **Where:** [results-draft.ts:105](../src/lib/results-draft.ts#L105) (`saveDraftResults`, override upsert at [:109](../src/lib/results-draft.ts#L109)); also [episode-publication.ts:52-56](../src/lib/episode-publication.ts#L52), [schema.sql:3624](../supabase/schema.sql#L3624), [results-form.tsx:396-419](../src/components/results-form.tsx#L396).
- **What's wrong:** `saveDraftResults` never checks `results_published_at`. It upserts `draft_episode_overrides` and writes only the couples in `entries`. If an autosave waits on `commit_episode_publication`'s table lock, or lands just after the commit, it recreates a draft on the now-published episode holding one couple's rows (the commit already deleted the old draft). `startCorrection` can leave the same thing: it inserts the override before the dances and results, so a failure mid-seed leaves a partial draft. Either way `hasDraft` is now true, so Enter Results hydrates from the partial draft instead of seeding a correction. The commit RPC treats the draft as the whole night: it deletes every live dance not in the draft (`v_preserved` is empty once published), replaces all `episode_results`, and resets couples whose resolving outcome disappeared back to active.
- **Why it matters:** Commissioners are still typing when the super admin publishes. A later correction Publish on that episode, even a one-couple fix, deletes the other couples' dances and outcomes, un-eliminates the eliminated couple and recomputes every league's week. Nothing warns: `unposted` is empty for a published episode and `entries.length > 0`.
- **Fix:** In `saveDraftResults`, refuse when the episode is published and no correction-draft override exists (or require a token from `startCorrection`). In `commit_episode_publication` / `buildPublicationPlan`, refuse a correction whose `draft_episode_results` doesn't cover every couple that has live `episode_results` or `dance_scores`.
- **Evidence:** Code at the lines above. PGlite with the real RPCs (`audit2/backend/publication-multi.test.ts`, "a one-couple draft on a published episode republishes as the whole night"): `before 4 after [ { couple_id: ...22, outcome: 'safe' } ] A now { status: 'active', elimination_week: null }`. The original test loaded `apply-atomic-episode-publication.sql`; the verifier reproduced the same outcome with the whole HEAD `schema.sql`. Live, read-only: the existing correction drafts on E01 and E03-E06 match live (0 dance and 0 outcome mismatches), so nothing is armed today. Verifier: 1/1 upheld; corrected the delete line to 3624 and added the `startCorrection` mid-seed trigger.

**BE-4 · Multi-episode week: publishing night 2 drops night 1's Grand Finale credit, and revealing night 2 zeroes the week's Curtain Call and Grand Finale** — Medium
- **Where:** [weekly-score-rows.ts:73-75](../src/lib/weekly-score-rows.ts#L73); also [weekly-score-rows.ts:117](../src/lib/weekly-score-rows.ts#L117) and [:138-184](../src/lib/weekly-score-rows.ts#L138), [results.ts:243-251](../src/lib/results.ts#L243), [episode-publication.ts:49](../src/lib/episode-publication.ts#L49), [score-history.ts:197](../src/lib/score-history.ts#L197), [recompute-published-weeks.ts:84-90](../scripts/recompute-published-weeks.ts#L84).
- **What's wrong:**
  - `buildWeeklyScoreRows` takes `newlyResolvedCoupleIds` only from `thisEpisodeOutcomeRows` and computes Grand Finale only from those. The commit replaces the week's whole `weekly_manager_scores` row, so publishing a week's second episode keeps only that night's Grand Finale credits.
  - `recomputeWeekForReveal` passes `[]` with `reveal: true`, which drops Curtain Call predictions, Grand Finale, this episode's stored outcomes and In Jeopardy data (line 117 empties it). Posting any couple on night 2 rewrites a week whose night 1 is already published, so its stored Curtain Call and Grand Finale points go to 0 until the final publish.
  - Score History credits every resolved couple in the week, so its lines and the stored totals diverge.
  - `scripts/recompute-published-weeks.ts` makes the same assumption: it picks the first episode with a resolving outcome as "this" episode, so a retroactive recompute also drops the other night's credit.
- **Why it matters:** The data model supports multi-night weeks, and Week 1 this season was two nights with an elimination on each. A future two-night week with eliminations would permanently underpay every Grand Finale league. During a second-night reveal, Standings and Home would show managers losing their Curtain Call points live.
- **Fix:** Derive resolved couples from all of the week's outcomes (the week's other episodes plus this one), in both `buildWeeklyScoreRows` and the recompute script. In reveal mode, keep predictions, Grand Finale credit and In Jeopardy data from the week's already-published episodes, or build reveal mode on the stored row plus a judges delta.
- **Evidence:** PGlite with the real commit RPC (`publication-multi.test.ts`): `expected week GF with both nights' eliminations: 16.66 stored: 8.33`. The reveal case through the fake client end to end (`reveal-week.test.ts`): `before ... prediction_points: 10.35, grand_finale_points: 8.33 ... after ... prediction_points: 0, grand_finale_points: 0` (the PGlite reveal case produced no row because that test had no roster). Live, read-only: Week 1 = E01 + E02, each with 1 resolving outcome; every Grand Finale league has anchor week 2 and weeks 6-11 are single episodes, so there's no live damage now. Verifier: 1/1 upheld; added the recompute script and the In Jeopardy loss.

**BE-6 · `saveDraftResults` ignores its delete errors and isn't last-write-wins: dances duplicate** — Medium
- **Where:** [results-draft.ts:134-135](../src/lib/results-draft.ts#L134); also the inserts at [results-draft.ts:140-177](../src/lib/results-draft.ts#L140), [results-draft.ts:291-296](../src/lib/results-draft.ts#L291) (`deleteAllDraftRows`), [results-form.tsx:638-643](../src/components/results-form.tsx#L638).
- **What's wrong:** The scoped deletes of `draft_dance_scores` and `draft_episode_results` are awaited with their errors discarded, then the dances are inserted one by one. If a delete fails, the save inserts a second copy of the couple's dances and reports success. Two same-couple saves that interleave (delete A, delete B, insert A, insert B) leave the union of both dance sets; only the second `draft_episode_results` insert fails, and the client keeps that couple dirty with no automatic retry (it re-flushes only on the next edit). `draft_dance_scores` has no unique key ([schema.sql:2431-2440](../supabase/schema.sql#L2431)). `deleteAllDraftRows` ignores its delete errors the same way.
- **Why it matters:** A duplicated draft dance doubles that couple's judges points in draft standings for fans who unlocked drafts. Reveal copies every draft dance live, and a correction publish installs the duplicates into live `dance_scores` and every league's score. CLAUDE.md accepts last-write-wins for same-couple edits; a union is a different and worse failure, and on a live night several commissioners type the same couple's scores as they're read out. The union lasts until someone edits that couple again (that save's delete clears all its rows).
- **Fix:** Do the per-couple replace in one RPC transaction (delete + insert) with an advisory lock on `(episode_id, couple_id)`. Checking the delete errors alone covers the failed-delete case but not the race. Consider a unique key on `draft_dance_scores (episode_id, couple_id, slot)`.
- **Evidence:** Fake client (`backend-races.test.ts`), single save with a failed delete: `second save error: null draft dances: 4` for a two-dance couple. Interleaved saves: `offset=0 draftDances=4 ... A.err=null B.err=duplicate key value violates unique constraint on draft_episode_results`. `races.test.ts`: `200 concurrent same-couple saves: 195 left >1 draft dance for a one-dance couple`. The fake client shows the sequencing, not real Postgres locking; the code trace establishes the race on its own, since nothing between the delete and the inserts takes a lock or opens a transaction. Verifier: 1/1 upheld.

**BE-7 · Correction seeding ignores read errors and isn't atomic: a correction draft can lose dances, and republishing then deletes them live** — Medium
- **Where:** [results-draft.ts:354-372](../src/lib/results-draft.ts#L354) (`startCorrection`); also [results-draft.ts:196-212](../src/lib/results-draft.ts#L196) (`loadDraftForEpisode`), [results-form.tsx:396-419](../src/components/results-form.tsx#L396), [schema.sql:3624](../supabase/schema.sql#L3624).
- **What's wrong:** `startCorrection` destructures the live `dance_scores`, `episode_results`, moments and In Jeopardy reads without their errors; only the episode read is checked. If the dances read fails, it seeds a correction draft with results but zero dances and returns success. The seed is also a series of separate deletes and inserts, so a mid-way failure leaves a partial draft that `hasDraft = true` makes permanent. Separately, `loadDraftForEpisode` ignores its read errors: a failed override read reports "no draft", and the client re-seeds the published episode, discarding an in-progress correction (it re-copies from live, so only the edits are lost). A failed `draft_dance_scores` read gives `hasDraft = true` with no dances, which only misleads the display, since publish reads the database draft tables.
- **Why it matters:** The super admin opens a published week in Enter Results while the API is flaky. The correction draft silently has no dances, and the read-only cards don't make that obvious. They unlock one couple and Publish Results, and `commit_episode_publication` deletes every live dance not in the draft: judges points for that week disappear across every league.
- **Fix:** Check every read's error before `deleteAllDraftRows`. Move the seed into an RPC that copies live to draft in one transaction. Make `loadDraftForEpisode` throw on read errors so the client never mistakes an error for "no draft".
- **Evidence:** Fake client (`backend-races.test.ts`): `startCorrection: { error: null } draft overrides: 1 draft results: 1 draft dances: 0 live dances: 1`. `races.test.ts`: `loadDraftForEpisode` with a failed override read returns `hasDraft` false. PGlite (`publication-multi.test.ts`, "a correction draft missing couples' dances deletes their live dances on republish"): `live E3 dances after correction publish: 1 (was 2)`. Verifier: 1/1 upheld; corrected the delete line to 3624 and separated the data-loss path (the dances read) from the lower-impact `loadDraftForEpisode` paths.

**BE-8 · Reveal and Un-Post recompute every league with separate delete/insert calls; a failure leaves points that don't match the live dances** — Medium
- **Where:** [results.ts:292-300](../src/lib/results.ts#L292); also [results-reveal.ts:124-128](../src/lib/results-reveal.ts#L124) and [:139-144](../src/lib/results-reveal.ts#L139).
- **What's wrong:** `recomputeWeekScores` loops over leagues, deleting and then inserting each league's `weekly_manager_scores` as separate PostgREST calls, with no transaction. If league 2's insert fails during a reveal, `revealCouple` deletes the couple's live dances but never recomputes: league 1 keeps points for a dance that's no longer live, and league 2 is left with no row for the week at all, losing the points from couples revealed earlier that night. `undoReveal` deletes the dances first and then returns the recompute error, so the points stay up with the dances gone. - **Where:** [schema.sql:1377-1386](../supabase/schema.sql#L1377) (fellow-member policy); also [schema.sql:726](../supabase/schema.sql#L726) (table-wide grant), [apply-co-manager.sql:110-118](../supabase/apply-co-manager.sql#L110).
- **What's wrong:** `profiles` has a table-wide `grant select … to authenticated`, and the "viewable by fellow league members" policy exposes whole rows. RLS can't scope columns, so any leaguemate can read `is_super_admin`, `deletion_requested_at` (a pending account-deletion request) and `spoiler_free_mode`, not just `display_name` and `avatar_url`.
- **Why it matters:** Any member can see from the REST API who the site admins are (a phishing target, since a super admin can publish results and open late entries in any league) and who has quietly asked to delete their account. Neither is shown in the UI.
- **Fix:** Keep the owner policy for full rows, and serve peers through a view or security-definer function returning only `id`, `display_name` and `avatar_url`; point the `profiles!league_members_*_fkey(display_name)` joins at it. A plain column revoke would break own-row readers (League Settings' `is_super_admin` at `settings/page.tsx:48`, admin results/accounts actions, `account-settings-data.ts:31`, `score-history-data.ts:35`, the settings pages). `apply-co-manager.sql` re-creates the same policy, so cover it too.
- **Evidence:** Live, read-only: `has_column_privilege('authenticated','public.profiles',col,'SELECT')` is true for all 7 columns (`id`, `display_name`, `avatar_url`, `is_super_admin`, `created_at`, `deletion_requested_at`, `spoiler_free_mode`). Own-row readers found with grep `from("profiles")`. Verifier: 1/1 upheld; added the `apply-co-manager.sql` copy.

**BE-24 · Undo Last Pick removes whatever pick is newest, so it hits an autopilot pick that landed a second after the one the commissioner meant** — Low
- **Where:** [schema.sql:2279-2290](../supabase/schema.sql#L2279) (`undo_last_pick`); also [use-auto-draft-pick.ts:7](../src/lib/use-auto-draft-pick.ts#L7) and [:26-43](../src/lib/use-auto-draft-pick.ts#L26), [draft-room.tsx:520](../src/components/draft-room.tsx#L520).
- **What's wrong:** `undo_last_pick` takes no expected pick; it deletes `order by pick_number desc limit 1` and resets the clock. Autopilot fires `make_auto_draft_pick` 1s after each pick from any open draft-room client, and after an undo the same autopilot manager is back on the clock, so it re-picks within a second. The Undo button sits on the last pick's row, so the window is about 1s plus realtime latency. The client's optimistic `slice(0, -1)` removes the pick it showed as last, so in this race the commissioner's board drifts from the server until a reload.
- **Why it matters:** Alice makes pick 5 by mistake. Bob, on autopilot, gets pick 6 a second later. The commissioner taps Undo meaning pick 5 and removes Bob's pick 6; Bob's autopilot picks again and pick 5 stays. Even without a race, a mistaken pick followed by an autopilot pick can't be undone until that member's autopilot is turned off (`set_member_draft_autopilot`), which isn't obvious mid-draft.
- **Fix:** Pass the pick the commissioner saw (`p_expected_pick_number`, or the pick id, which also lets the client reconcile its local state) and raise "A newer pick landed — refresh" when the newest pick differs.
- **Evidence:** Code-path analysis, not run: `schema.sql:2256-2294` and `use-auto-draft-pick.ts:7`, `:26-43`. Verifier: 1/1 upheld; added the client-state drift and the autopilot-refill limit.

**BE-25 · Propose tier is reachable by any signed-in account through `create_league`** — Medium

**BE-26 · A planted or stale correction draft is installed wholesale by the admin's next correction publish** — Medium
- **Decision:** "Correcting a published episode is narrowed to one couple at a time … re-publishing applies whatever's in the draft regardless of which couples were ever unlocked" (CLAUDE.md, live score reveal paragraph).
- **Where:** [episode-publication.ts:47-56](../src/lib/episode-publication.ts#L47) and [:131-141](../src/lib/episode-publication.ts#L131); also [results-draft.ts:105](../src/lib/results-draft.ts#L105), [results-form.tsx:398](../src/components/results-form.tsx#L398) and [:784](../src/components/results-form.tsx#L784), [schema.sql:3618-3640](../supabase/schema.sql#L3618).

- **Evidence:** Code at the lines above. Live, read-only: correction drafts exist for E01 and E03-E06 and match live (0 mismatches). Verifier: 1/1 upheld; corrected the secondary line to 105 and added the partial-draft data-loss extension.
